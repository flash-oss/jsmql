## 2026-10-17 — fix: an unknown method suggests a method, never a global

An unknown method after a dot drew its suggestion from every JavaScript name, globals
included. So `$.x.toNumber()` suggested `.Number()`, and before the conversion methods
`$.x.toDouble()` suggested `.Double()`. A global is not a method, and neither is a static
of a namespace such as `Array.isArray`. `everyMethodName` in
[src/compiler/emit/consult.ts](../../src/compiler/emit/consult.ts) lists the rows that a
value calls after a dot, and the value road and the statement road both read it.

```
$.x.toDoubel()      Unknown method '.toDoubel()' …. Did you mean '.toDouble()'?
$.x.toNumber()      Unknown method '.toNumber()' ….          (no '.Number()')
```

## 2026-10-17 — feat: the conversion methods `.toDouble()` … `.toUUID()`

Each MongoDB conversion operator now has a method with its name: `.toDouble()`,
`.toInt()`, `.toLong()`, `.toDecimal()`, `.toBool()`, `.toDate()`, `.toObjectId()` and
`.toUUID()`, beside `.toString()`. The developer chose these names in the interview on
this day. There is no `.toNumber()`, because the MongoDB name says which type the
developer gets.

```
$.x.toDouble()        { $toDouble: { $ifNull: ["$x", 0] } }       → 0 for a missing x
$.x.toBool()          { $toBool: { $ifNull: ["$x", false] } }     → false
$.x.toDate()          { $toDate: { $ifNull: ["$x", new Date(0)] } } → the epoch
$.x.toObjectId()      { $toObjectId: "$x" }                       → null: an ObjectId has no safe value
$.x?.toDouble()       { $toDouble: "$x" }                         → null
```

Each row states the safe value of the kind that it gives, and `passesNull`. The three
tables in [test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) measure
each fact on mongod. `.toBool()` is MongoDB's `$toBool`: mongod gave `true` for `""` and
for `"false"`. JavaScript's `Boolean("")` is `false`.
[docs/LANGUAGE.md](../LANGUAGE.md) states the difference, and names `!!$.x` for the
truthiness of JavaScript. The globals generator declares the methods on `String`,
`Number`, `Date` and a new `Boolean` block, so a typed document completes them.

## 2026-10-17 — feat!: a date method reads a missing date as the epoch

HR5 now gives a date the safe value of the epoch, `new Date(0)`. The developer chose the
epoch over `null` in the interview on this day. Under a dot, the compiler wraps a date
receiver in `{ $ifNull: [<recv>, new Date(0)] }`. The method then runs on the epoch:

```
$.t.getFullYear()       // { $year: { $ifNull: ["$t", new Date("1970-01-01T00:00:00.000Z")] } }   → 1970
$.t.plus(1, "day")      // the startDate reads the epoch                                       → 1970-01-02
$.t?.getFullYear()      // { $year: "$t" }                                                    → null
```

Each date row has one family, so `dispatchOn` adds the wrap. `.clamp()` and `.inRange()`
serve a number and a date. So the kind of their bounds picks the safe value: the epoch
for a date bound, and 0 for any other bound. The cell adds no wrap where the bounds give
the answer of `null`. The Filter of `.inRange()` matches a missing field where a date
range contains the epoch. The safe value has two effects that a developer can see. A
`??` after a date method under a dot never falls back, so the realistic example
"formatted date label with ?? chain" now writes `$.publishedAt?.format(…)`. A `$group`
on `$.createdAt.startOf("month")` counts a document with no `createdAt` in the bucket of
the epoch. The chain suite in
[test/compiler-chains.test.ts](../../test/compiler-chains.test.ts) adds `.getTime()`
and a date at each level, and every chain runs on mongod.

## 2026-10-17 — feat: an `$elemMatch` body keeps `$or` over the fields of an element

The `.some()` cell refused every `$and`, `$or` and `$nor` in its body, so
`$.items.some(i => i.q > 2 || i.r === 1)` took the `$expr` road, and no index served it.
mongod refuses these operators only over tests of the element itself, and it accepts
them over the fields of an element. The number fix of this day also writes an `$or` into
such a body for `.inRange()`. The cell now keeps a body over fields:

```
$.items.some(i => i.q > 2 || i.r === 1)    { items: { $elemMatch: { $or: [{ q: { $gt: 2 } }, { r: 1 }] } } }
$.items.some(i => i.n.inRange(10))         { items: { $elemMatch: { $or: [{ n: { $gte: 0, $lt: 10 } }, { n: null }] } } }
$.items.some(i => !(i.q === 1))            { items: { $elemMatch: { $nor: [{ q: 1 }] } } }
$.tags.some(t => t === "a" || t === "b")   { $expr: … }    the element itself, refused in a body
```

Three new rows in
[test/compiler-query-expr-agreement.test.ts](../../test/compiler-query-expr-agreement.test.ts)
run both forms on mongod over a new field `it`, which holds element documents.

## 2026-10-17 — feat!: a number method reads a missing number as `0`

HR5 now gives a number the safe value `0`. Under a dot, the compiler wraps a number
receiver in `{ $ifNull: [<recv>, 0] }`, as it wraps a string in `""`. The method then runs
on `0`. The developer chose `1` for an operator that refuses `0`, as lodash's `_.divide()`
reads a missing divisor. mongod refused `0` for four methods only: `.log()`, `.log2()`,
`.log10()` and `.acosh()`. Their rows state `nullReceiverAs: 1`.

```
$.n.round(2)          // { $round: [{ $ifNull: ["$n", 0] }, 2] }      → 0
$.n.log()             // { $ln: { $ifNull: ["$n", 1] } }              → 0
$.n?.round(2)         // { $round: ["$n", 2] }                        → null
$.n.inRange(10)       // the expression reads 0, which is in [0, 10)  → true
$.n.clamp(0, 100)     // { $min: [{ $max: ["$n", 0] }, 100] }         → 0, with no wrap
```

`.clamp()` and `.inRange()` take a number or a date, so the cell wraps the receiver
itself (`safeNumber`). It adds no wrap where two constant bounds make `0` give the answer
that `null` gives. The Filter of `.inRange()` follows the rule of the string fix: a range
that contains `0` also matches a missing field, `{ $or: [{ n: { $gte: 0, $lt: 10 } }, { n: null }] }`.
`.range()`, `.rangeRight()`, `.sign()` and `.random()` read `0` from the family of their
rows now, so they state no `nullReceiverAs`. This change removes the `NullAnswer` type,
because a row can state both facts: `$.n?.log()` is `{ $ln: "$n" }`. The chain suite in
[test/compiler-chains.test.ts](../../test/compiler-chains.test.ts) adds `.abs()` and a
number at each level, and every chain runs on mongod.

## 2026-10-17 — fix: `.has(null)` in a query clause does not match a missing array

A dot reads a missing or `null` array as `[]` (HR5), and `[]` holds no `null`. So the
expression form of `$.tags.has(null)` is false for a document with no `tags`. The query
form was `{ tags: null }`, and that clause matches a missing or `null` field. So a Filter
selected documents that the expression form did not select. This is the reverse case of
the fix [a query clause matches a missing string where its test is true for `""`](#2026-10-17--fix-a-query-clause-matches-a-missing-string-where-its-test-is-true-for-).
A null needle now tests the elements alone:

```
$.tags.has(null)                       { tags: { $elemMatch: { $eq: null } } }
$.tags.has(null) && $.tags.has("a")    { tags: { $all: [null, "a"] } }       "a" excludes a missing field
$.m.some(r => r.has(null))             { m: { $elemMatch: { $elemMatch: { $eq: null } } } }
```

An `$all` list of null needles alone also matches a missing field. So `extractHasChain` in
[src/compiler/emit/filter.ts](../../src/compiler/emit/filter.ts) keeps the clause of each
leaf for such a chain. mongod selected the same documents for each query form and its
expression form. The documents included nested arrays. A new field `h` in
[test/compiler-query-expr-agreement.test.ts](../../test/compiler-query-expr-agreement.test.ts)
holds an array, `null`, or nothing, because `$in` stops the command on a string `tags`.

## 2026-10-17 — fix: a query clause matches a missing string where its test is true for `""`

A dot reads a missing or `null` string as `""` (HR5), so the expression form of
`$.s.match(/^$/)` is true for a document with no `s`. The query form `{ s: { $regex: /^$/ } }`
never matched that document, so a Filter and an expression of one source selected
different documents. The developer chose this fix on this day. The compiler keeps the
query form. It adds the null test only where the test is true for the safe value. A regex
test and the null test share one `$in`. This `$in` is shorter than the `$or` of the
interview example. An `$elemMatch` body over a value can also contain this `$in`. mongod
selected the same documents for the `$in` and the `$or`.

```
$.s.match(/^$/)                    { s: { $in: [/^$/, null] } }
$.s.includes("")                   { s: { $in: [/(?:)/, null] } }
$.tags.some(t => t.includes(""))   { tags: { $elemMatch: { $in: [/(?:)/, null] } } }
$.s?.match(/^$/)                   { s: { $regex: /^$/ } }          a `?.` gives null
$.a?.b.includes("")                { $expr: … }                     a `?.` earlier in the path
$.s.match(/a/)                     { s: { $regex: /a/ } }           the test fails on ""
```

The new `FilterIn` service `orMissing` contains the rule for `.includes()`, `.startsWith()`,
`.endsWith()` and `.match()`. The compiler runs a regex on `""` with JavaScript. The server
matches the PCRE anchors `\A`, `\z`, `\Z` and `\G` on `""`, so the compiler reads each one
as an empty group before the run. Seven new rows in
[test/compiler-query-expr-agreement.test.ts](../../test/compiler-query-expr-agreement.test.ts)
run both forms on mongod.

## 2026-10-17 — feat: a `?.` read takes no `$ifNull` where the consumer passes null

A `?.` read with no call after it is `{ $ifNull: [x, null] }`, so a missing value reads
as `null`. Many consumers give the same answer for missing and for `null`, and the wrap
adds nothing there. The productions of `+` on numbers, `-`, `*`, `/`, `%`, `**`, `-x` and
`??` now state `passesNull`. A test in
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) measures each one on
mongod. `== null`, `!= null` and every truth test read the operand the same way.
`== null` is now the short null test itself:

```
$.b?.c ** 2       → { $pow: ["$b.c", 2] }                 (was { $pow: [{ $ifNull: ["$b.c", null] }, 2] })
$.b?.c ?? 0       → { $ifNull: ["$b.c", 0] }
$.b?.c == null    → { $lte: ["$b.c", null] }              (was a $type test against "null" and "missing")
$.b?.c ? 1 : 2    → { $cond: [{ $and: [{ $gt: ["$b.c", null] }, …] }, 1, 2] }
$.b?.c === 1      → { $eq: [{ $ifNull: ["$b.c", null] }, 1] }   (kept: $eq tells missing from null)
```

`{ $eq: [null, null] }` is true. The `.join()` element test uses the short null test too.

## 2026-10-17 — feat: a shorter null test, and `$cond` in its array form

The developer asked for the shortest MQL of `?.`. Two shapes in every program get
shorter. The null test of `?.` and of a string method is `{ $lte: [x, null] }` in place
of `{ $eq: [{ $ifNull: [x, null] }, null] }`. Its negation in the JavaScript truthiness
check is `{ $gt: [x, null] }`. Null sorts below every other value but `MinKey`, so one
comparison covers missing and null. The mongod server gave the same answer for both
tests on a missing value, `null`, `0`, `""`, `false`, `[]` and `{}`. Only a `MinKey` value
reads as null now, and the developer accepts that.

The compiler writes each `$cond` in the array form `[if, then, else]`, in place of the
object `{ if, then, else }`. The developer's own `$cond(…)` call keeps the object form
that HR2 gives it, because it is the developer's MQL.

```
$.s?.trim()     → { $cond: [{ $lte: ["$s", null] }, null, { $trim: { input: "$s" } }] }
$.a ? 1 : 2     → { $cond: [{ $and: [{ $gt: ["$a", null] }, { $ne: ["$a", false] }, …] }, 1, 2] }
```

## 2026-10-17 — feat!: a string method reads a missing string as `""`

HR5 now gives a string the safe value `""`. Under a dot, the compiler wraps a string
receiver in `{ $ifNull: [<recv>, ""] }`, as it wraps an array in `[]` and an object in

## 2026-10-17 — docs: HR5 gives every kind of receiver a safe value under a dot

HR5 had a string exception: a string method gave `null` on a missing string, with the
reason that JavaScript throws there. The developer rejected the reason. JavaScript also
throws for an array or an object method on `null`, and lodash answers each of them
safely: `_.upperCase(null)` is `""`. The developer started JSMQL to remove unexpected
`null`s, so the rule must be the same for every kind of receiver.

HR5 now gives one table of safe values. An array reads `[]` and an object reads `{}`. A
string reads `""`. A number reads `0`, or `1` where the operator refuses `0`, as lodash's
`_.divide()` reads a missing operand as `1`. A date reads the epoch. A kind with no safe
value, for example an ObjectId, gives `null`, and `?.` gives `null` for every kind.

The developer decided each value in an interview. The interview also decided that the
type names are no longer conversion functions: JSMQL refuses `Number($.x)` and names
`$.x.toDouble()`. It also decided that the BSON constants (`new Date("…")`, `ObjectId("…")`) stay
as they are for now. The code follows HR5 in the commits after this one.

## 2026-10-17 — feat: `.random()` is lodash's `_.random` on a number

`x.random()` gives a number from 0 to `x`. `x.random(y)` gives a number between `x` and
`y`. Both match lodash's `_.random(x)` and `_.random(x, y)`. The bounds swap when the first is larger.
lodash gives a whole number, both ends included, when both bounds are whole, and a
fractional number otherwise. The developer picked that rule, tested at run time. Two constant
bounds decide the form at compile time. For bounds from a document, the MQL holds a `$let` of
the two ends, and the server runs a `$cond` whole-number test. A missing bound reads as `0`,
as lodash reads it, so the row states `nullReceiverAs: 0`.

```
(1).random(6)       → { $add: [1, { $floor: { $multiply: [{ $rand: {} }, 6] } }] }
(5).random()        → { $floor: { $multiply: [{ $rand: {} }, 6] } }
(1.5).random(2)     → { $add: [1.5, { $multiply: [{ $rand: {} }, 0.5] }] }
$.a.random($.b)     → { $let: { vars: { jsmqlLo: { $min: […] }, jsmqlHi: { $max: […] } }, in: { $cond: … } } }
```

A test in [test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) runs each
form 400 times on mongod. It checks the range, both whole ends, and the whole or
fractional answer. `Math.random()` stays `{ $rand: {} }`. JSMQL does not take lodash's
third argument, `floating`.

```
$.n.round()              → { $round: "$n" }                                  (was ["$n", 0])
$.n.floor(1)             → { $divide: [{ $floor: { $multiply: ["$n", 10] } }, 10] }
$.x.cbrt()               → { $multiply: [{ $cmp: ["$x", 0] }, { $pow: [{ $abs: "$x" }, 0.3333333333333333] }] }
$.x.sign()               → { $multiply: [{ $cmp: ["$x", 0] }, { $pow: ["$x", 0] }] }
$.x.log(10)              → { $log10: "$x" }
$.raw.trunc(2).log10()   → { $log10: { $trunc: ["$raw", 2] } }
```

`Math.sign($.x)` was `{ $cmp: ["$x", 0] }`, and the server gives `-1` for a missing
`x`. The new shape multiplies by `{ $pow: [x, 0] }`. That factor is `1` for a number and
`null` for a missing value. So `.sign()` gives `null` there, as the other arithmetic
methods do. The developer picked it over a `$cond`, because it is shorter. Because the
shape already gives `null` for `null`, the `.sign()` row states `passesNull` too, and
`$.x?.sign()` takes no `$cond`. The task planned `.sign()` without the fact. The guard
table wanted the same shape under `?.`, and the fact gives that shape. Each other
new number row states `passesNull`, and
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) measures each one.

A constant precision of `.ceil(n)` and `.floor(n)` folds the scale (`10` in place of
`{ $pow: [10, 1] }`). The mongod server gives `10 ** p` for `-7 ≤ p ≤ 15`. The fold of
a constant moves to the number methods (`(3).abs()` is `3`), for the methods whose
answer IEEE-754 specifies. The reducer wrap reads `[acc, d.x].max()` as `$max`, and
the update document reads `$.n = [$.n, 3].min()` as `$min`. A bare `Math.floor` value
or callback (`$.a.map(Math.floor)`) answers with the row's refusal. A misspelled static
never suggests a refused member. The integer hint of `.range()` names `.ceil()` and
`.floor()`.

## 2026-10-17 — feat!: the receiver methods replace the `Object` statics

JSMQL had two spellings for each object reader: the JavaScript static and the method of
the receiver. The developer's rule is "one capability gets one spelling, and the shorter
spelling wins". The method is shorter in each case, so `Object.keys`, `Object.values`,
`Object.entries`, `Object.fromEntries` and `Object.assign` are no longer JSMQL names.
They still parse, and the `Object` cell of each row refuses the call and names the
method, as `Object.groupBy` does. The `Object` root row stays, because the refusal
needs the name to parse. A suggestion for a misspelled static never names a refused
static now (`lowersOn` in [src/compiler/rows.ts](../../src/compiler/rows.ts)).

```
Object.keys($.doc)           ✗ write $.doc.keys()
Object.assign(...$.docs)     ✗ write ({}).assign(...$.docs)
Object.assign($.f, $.x);     ✗ write $.f = { ...$.f, ...$.x };
({}).assign(...$.docs)       → { $mergeObjects: "$docs" }
({}).assign($.o)             → { $mergeObjects: ["$o"] }
$.a.assign(...$.docs)        → { $mergeObjects: { $concatArrays: [["$a"], { $ifNull: ["$docs", []] }] } }
$.o.keys()                   → { $map: { input: { $objectToArray: { $ifNull: ["$o", {}] } }, in: "$$this.k" } }
$.p.fromEntries()            → { $arrayToObject: { $map: { input: { $ifNull: ["$p", []] }, in: [{ $toString: { $first: "$$this" } }, { $arrayElemAt: ["$$this", 1] }] } } }
```

`.assign()` reads a spread argument as a list of sources and a plain argument as one
source. Before, `({}).assign(...$.docs)` emitted `{ $mergeObjects: [{}, "$docs"] }`, and
the server rejects that when `docs` is an array. An empty receiver is now dropped.
After a real receiver, a spread list takes the HR5 guard of the array literal. Without
it, the server answers `{}` for `{ $mergeObjects: { $concatArrays: [["$o"], "$nope"] } }`,
so the receiver is lost. The mongod server also merges `{ $mergeObjects: ["$docs"] }`
as one list, so `["$o"]` and `"$o"` give the same answer for one plain source.

`.assign()` writes nothing in place, so the desugar rule that turned
`Object.assign(t, …);` into a write is gone, with the `mutatesArgumentAt` row fact.
lodash's `_.assign` writes its target, so a lone `$.p.assign(…)` or `r.assign(…);` is
still a statement, and the statement cell refuses it and names the write back.
`.keys()`, `.values()`, `.entries()`, `.toPairs()` and `.fromEntries()` read `$$this`
in place of a minted name, because each `in` body is fixed compiler text. The fold
now folds the method forms on a constant: `({ a: 1 }).keys()` is `["a"]`.

## 2026-10-17 — docs: HR5 states the number rule

HR5 gave the dot and `?.` answers for an array, an object and a string, but not for a
number. The developer's reading of the dot rule is "a dot gives the safe value, as
lodash does". [docs/LANG_RULES.md](../LANG_RULES.md) now states the dot rule for a number. A
number method on a missing or `null` receiver gives the safe value where one exists,
and `null` where none exists. `.clamp()` gives its lower bound, `.inRange()` gives
`false`, and `.range()` gives `[]`. The arithmetic methods, for example `.round()`,
have no safe value, so they give `null`. The mongod server gave these answers for `{}`:

```
$.n.clamp(0, 9)     → { $min: [{ $max: ["$n", 0] }, 9] }   → 0
$.n.round(2)        → { $round: ["$n", 2] }                → null
$.n?.clamp(0, 9)    → a $cond null test                    → null
```

The rule changes no MQL. It records the behaviour that the number rows already have,
before the `Math` members move onto the number receiver.

## 2026-10-01 — feat!: the value-taking `Math` members move onto the number

JSMQL spelled each numeric operation two ways: a `Math` static (`Math.abs($.x)`) and,
for some of them, a number method (`$.x.round()`). One capability gets one spelling,
and the shorter spelling wins. JSMQL refuses every `Math` member that takes a value,
and its refusal names the method that emits the identical MQL. `Math` keeps the three
members that take no value: `Math.random()`, `Math.PI` and `Math.E`.

```
$.delta.abs()         // { $abs: "$delta" }
Math.abs($.delta)     // ✗ names $.delta.abs()
[$.a, $.b].max()      // { $max: ["$a", "$b"] }
$.x ** 2              // { $pow: ["$x", 2] }      — Math.pow is refused, and names **
$.raw.trunc(2)        // { $trunc: ["$raw", 2] }
$.x.log(10)           // { $log10: "$x" }         — .log(b) takes a base
```

Each moved row is on the number family and on `Math`. The number cell emits the old
lowering with the receiver as the first operand, and the `Math` cell refuses. The name
is unique to the number family, so an unproven receiver such as `$.delta` takes the
number rule. The developer also decided that a bare `Math` member is not a callback:
JSMQL refuses `.map(Math.floor)`, and the arrow `.map(x => x.floor())` is the one spelling.
The `.reduce` wrap reads `[acc, d.x].max()` as `$max`, and the update document reads
`$.n = [$.n, 5].min()` as `$min`, where both read `Math.max(…)` / `Math.min(…)` before.

`{ $round: "$n" }`. `.floor(p)` and `.ceil(p)` fold the scale `10 ** p` for a constant
integer `p`, and `.cbrt()` folds `1 / 3`. `.sign()` is
`{ $multiply: [{ $cmp: [x, 0] }, { $pow: [x, 0] }] }`: the `$pow` factor is 1 for a
number and null for nothing, so a missing receiver gives null with no `$cond`. Every
number row whose operator answers null for a missing operand states `passesNull`.
`.max()` and `.min()` state it too. So `$.n?.round()` is `{ $round: "$n" }`. `$.b?.c ** 2`
drops its `$ifNull`, because `$pow` answers null on its own. `.clamp()`, `.inRange()`
and `.range()` keep their safe dot answers and their `?.` test. Each moved method, the
two folded scales and `.sign()` on a missing field run on the project's mongod in
test/compiler-methods.test.ts, against JavaScript's own answer.

## 2026-10-01 — feat!: the `Object` statics give way to the object methods

JSMQL had two spellings for each object reading: a static (`Object.keys(o)`) and a
method (`o.keys()`). Both emitted the same MQL. The developer decided that one
