## 2026-10-20 — fix: an arrow declared separately from `jsmql.compile(…)` type-checks

`const f = ({ d }, { $, $sum }) => …; jsmql.compile(f)` failed in TypeScript with
`TS2769`. The arrow given inline to the call type-checked. The toolbox type
`JsmqlToolbox` was an index signature over `` `$${string}` ``. An arrow declared separately
gets its own parameter type, with a required member for each name in the destructure.
An index signature cannot give a required member, so TypeScript refused the argument.

- `JsmqlToolbox` is now `any`. Every member of the old type was also `any`, so an inline
  arrow keeps the same types.
- The one-shot entries (`jsmql(f)` and the others) take the same toolbox type, so the
  change also applies to them.

## 2026-10-20 — feat: a thrown compile error shows the line, the column and the source line

A refusal such as the kind check of `Long(…)` told what was wrong, but not where. A
program with many calls to `Long(…)` gave the developer no way to find the fault from
the test runner output. Now each entry that throws adds a frame to the message and to the
stack:

```
CodegenError: <the message>
  at line 16, column 24:
16 |     cleared: $sum(Long($.wasCleared)),
                         ^
```

- One wrapper, `framed()` in `src/index.ts`, catches a `LexError`, a `ParseError` or a
  `CodegenError` and adds the frame from `.pos`. The wrapper keeps each tab of the source
  line in the caret line, because a test runner can give the arrow source with tabs.
- Line 1 is the first line of the source that the entry reads. For an arrow, that line
  is the arrow itself.
- `validate()` gives the message with no frame, because `.pos` already carries the
  position for a tool.
- Tests that compare the whole message remove the frame before the comparison.

## 2026-10-20 — feat: a whole number in an iteratee slot reads each element at that index

The answer for one class of input changes. Before this change, each iteratee slot refused
a number. Now a whole number in a slot that takes the field-name form compiles. It is
lodash's `_.property(n)`, and it means the arrow `x => x[n]`. The developer decided this:
`_.keyBy(rows, 5)` keys each row by `row[5]`.

- A new `SlotForm`, `propertyIndex`, sits beside `propertyPath` on each row whose layout
  lists `propertyPath`. Two stream cells do not list it: `.map` and `.flatMap` on a
  stream, because their arrow must return a document or name a field.
- The desugar pass rewrites the number to the arrow. A constant and an injected number
  reach the rule as a literal, so they mean the same arrow. The emitted MQL is the MQL of
  the arrow.
- The rewritten read carries the method and the slot. The emitter refuses the call
  when the proof shows that the elements cannot hold the index. The refusal uses the
  `wrongKind` wording. The elements can be of a kind with no index, such as numbers or
  strings. Or a list of fixed length can end before the index. An element of unknown
  kind is accepted. A document element is accepted too. The index reads the field with
  that name.
- A negative number or a fraction is refused with the same message, because JavaScript's
  `x[-1]` and `x[1.5]` read no element of an array.
- The refusal that lists the spellings of a slot now names the index too. Tests that
  used a number to get that refusal now use a boolean.

```js
$.rows.keyBy(5)              // ≡ $.rows.keyBy(x => x[5])
$.rows.groupBy(0)            // ≡ $.rows.groupBy(x => x[0])
[[1, 2], [3, 4]].keyBy(5)    // ✗ each element holds 2 items
[1, 2].keyBy(0)              // ✗ a number has no index
$.rows.keyBy(-1)             // ✗ x[-1] reads no element of an array
```

test/compiler-methods.test.ts runs the value cases on mongod and compares each answer
with lodash's answer, computed by hand.

## 2026-10-20 — fix!: refuse a fraction as the millisecond count of `new Date(…)`

This change turns inputs that compiled into refusals. `new Date(2020.5)` emitted
`new Date("1970-01-01T00:00:02.020Z")`. The developer decided that a fraction in that argument is a
typo. Measured on mongod: `$toDate` cuts a fraction toward zero (2020.5 gives 2020 ms, and
-2020.5 gives -2020 ms). JavaScript cuts it the same way. JSMQL does not cut a value
silently. The compiler now refuses a fraction that the source writes. It also refuses a fraction from a folded
expression, a `const` binding, a template value or a `jsmql.compile` parameter.
The refusal has the wording and the rounding hint of a fractional calendar part.

The cause was the date reader of the constant engine
([src/compiler/passes/date-literal.ts](../../src/compiler/passes/date-literal.ts)). It read
one constant number as an instant before any check ran, so the row had no chance to refuse
it. The reader now reads only a whole number, as it already did for the parts. The
constant cell of the `Date` row states the integer rule (`integer: [0]`), and `checkSlots`
reads it. A string, a date and a value of unknown kind convert as before.

```js
new Date(2020.5)          // ✗ a millisecond count is an integer; round it first
new Date(1700000000000)   // new Date("2023-11-14T22:13:20.000Z")
new Date($.n)             // { $toDate: { $cond: [{ $isNumber: "$n" }, { $toLong: "$n" }, "$n"] } }
```

## 2026-10-19 — fix: the root write, the stream map, the collection key and the sort slots use the one wording

More refusals of a value of the wrong kind used a different wording. Now each of them
calls `wrongKind` in [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts). The
advice of each old message is now the hint:

- A root write of a value that can never be a document, for example `$ = null;`,
  `$ = 1;` or `$ = [1];`. The write names no slot. An array keeps the hint that names
  `$$ = <array>;`.
- A `$$.map(…)` arrow that can never return a document. The slot is argument 1, and the
  kind is an arrow that returns a document.
- The key of `$$$[…]` that is not a string, from the source or from a parameter of
  `jsmql.compile`.
- A direction of the wrong kind in `.toSorted({ a: … })` and in the list of orders of
  `.orderBy()`, and a field name of the wrong kind in a sort list. A number or a string
  that is not a direction keeps the message that names each direction.
- The second argument of `.orderBy()`. The registry already refused it with the one
  wording. A new row fact, `slotHint`, adds the directions as the hint. Any row can state
  the hint of a slot in the same way.

```js
$ = null;                     // ✗ '$ = …' takes a document, but got null
$$ = $$.map(d => 1);          // ✗ argument 1 takes an arrow that returns a document
$$$[1] = $$;                  // ✗ the key of $$$[…] takes a string, but got a number
$.a.toSorted({ a: null })     // ✗ a takes a direction, but got null
$.a.orderBy("a", null)        // ✗ argument 2 … but got null, and the hint names 1, -1, "asc", "desc"
```

`$.a.sort(null);` reads its argument as `.toSorted()` does, so the message names
`.toSorted()`. It already used the one wording.

No input changes polarity. Each input that this entry names gets a refusal before and after
this change. Only the wording changes.

## 2026-10-19 — fix: a sort argument and a spread of a wrong kind use the one wording

Two refusals of a value of the wrong kind still used a different wording. Now each of
them calls `wrongKind` in [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts),
as the entry "fix: every refusal of a wrong kind has one wording" describes:

- A sort argument that can never be a name, a list or a document, for example `null`, a
  number, a boolean or a date. Every row that reads a sort argument reads it through
  [src/compiler/emit/sort-spec.ts](../../src/compiler/emit/sort-spec.ts). So
  `.sortBy()`, `.toSorted()`, `.sort()` and `.orderBy()` share one kind noun: "a sort
  specification". The reader now reads the proof of the argument. It also refuses a
  computed value that the proof shows to be a number. The hint names the spellings. An
  argument of another kind, for example a field read, keeps the message that names each
  spelling.
- The operand of a spread that can never be an array (`[...v]`) or a document
  (`{ ...v }`). The advice of the old message is now the hint. A spread of a value that the
  proof shows to be a string keeps its own refusal, because that refusal names another fix.

The hint of `.sortBy()` named the directions form `{ age: -1 }`. lodash's `sortBy` takes
no directions, and JSMQL refuses that form there. The hint of `.sortBy()` now names a key
function in its place.

```js
$.a.toSorted(null)   // ✗ argument 1 takes a sort specification, but got null
$.a.sortBy(1)        // ✗ argument 1 takes a sort specification, but got a number
$$.orderBy(true);    // ✗ argument 1 takes a sort specification, but got a boolean
[...null]            // ✗ '...' takes an array, but got null
({ ...[1] })         // ✗ '...' takes a document, but got an array
```

No input changes polarity. Each input that this entry names gets a refusal before and after
this change. Only the wording changes.

## 2026-10-19 — fix!: a fraction in a calendar part of `new Date(…)` is refused

This change turns inputs that compiled into refusals. `new Date(2020, 1.5)` emitted
`{ $dateFromParts: { year: 2020, month: 2.5 } }`, and mongod refuses that document
(HR3). Measured on mongod: `$dateFromParts` refuses a fractional double or Decimal128 in
each of the seven parts, and reads a whole double. JavaScript cuts the fraction off.
JSMQL does not cut a value silently. The compiler now refuses a written fraction and a
proven fraction. The refusal has the wording and the rounding hint of `.set({ month: 1.5 })`.

The cause was in the lowering of a global call (`dispatchBare` in
[src/compiler/emit/lower.ts](../../src/compiler/emit/lower.ts)). It selected the rule of
the row and emitted it, but it did not run `checkSlots`. So the `int` rule of the parts
slots had no reader for a global. `Date.UTC(…)` and `.set({ … })` do read it. Each
global call now runs the literal checks of its rule, as a method and a production do.
The refusal names the call as the source spells it, `'new Date()'` or `'Date()'`.

```js
new Date(2020, 1.5)       // ✗ each calendar part is an integer; round it first
new Date(2020, 1, 15)     // new Date("2020-02-15T00:00:00.000Z")
new Date(2020.5)          // one number is a millisecond count, and it converts as before
```

## 2026-10-19 — docs: HR7 states the null rule that the compiler upholds

The third consequence of HR7 in [docs/LANG_RULES.md](../LANG_RULES.md) said that the
compiler refuses a literal `null` where the slot needs a kind. The entry
[docs: HR7 — JSMQL refuses a value of the wrong kind](#2026-10-17--docs-hr7--jsmql-refuses-a-value-of-the-wrong-kind)
gave that text. The compiler upholds a wider rule now. A slot that takes a value other
than `null` refuses `null`. This is true for a written `null`, a `null` that the compiler
proves, and a `null` that the program passes in. A slot where `null` is data takes it, and
the escape hatch passes it as written, by HR2.

The consequence now states this rule. The examples of HR7 show a refused `null`, the same
`null` in the escape hatch, and a `null` that is data. [docs/LANGUAGE.md](../LANGUAGE.md)
already states the rule for the user, and points at HR7.

```js
$.a.slice(null)      // ✗ the start of .slice() takes an integer
$slice($.a, null)    // → { $slice: ["$a", null] }   as written, by HR2
$.a.has(null)        // → { $in: [null, { $ifNull: ["$a", []] }] }
```

No input changes polarity.

## 2026-10-18 — fix: every refusal of a wrong kind has one wording

The refusal of a value of the wrong kind has one form: the call as the source spells it,
the slot, the kind that the slot takes, and the value. `wrongKind` in
[src/compiler/emit/check.ts](../../src/compiler/emit/check.ts) builds it. Some refusals
kept a wording of their own. Now each of them calls `wrongKind`:

- A field name of a literal kind that is not a string, for example `$.o.pick([null])`.
  It now reads as the proven form `$.o.pick([$.o.b])` reads. A string that is empty,
  starts with `$` or holds a dot keeps its own refusal, because that is another fact.
- A `null` in a callback slot, for example `$.a.map(null)` or `$.a.groupBy(null)`. The
  slot names its own noun: "a callback", "a key" or "a predicate". A value of another
  kind keeps the message that names each spelling that the slot takes.
- A value that is not a document in `$$.push(…)`, `$$.concat(…)` and
  `$$$.<coll>.push(…)`. The hint that names the forms stays after the kind part.
- A constant of the wrong kind in `new Date(…)`. The constant cell of the date row is
  now a rule that states the kinds of its slot. A string that no date parser reads keeps
  its refusal, which names the two date constants.
- A key of `x[k]`. The row of the index access spells it `[…]`, and the slot is the key.

A refusal of a `new` call now names the call as `'new Date()'`, and a call without `new`
as `'Date()'`.

```js
$.o.pick([null])   // ✗ element 1 takes a field name, but got null
$.a.map(null)      // ✗ argument 1 takes a callback, but got null
$$.push(null);     // ✗ argument 1 takes a document, but got null
new Date(null)     // ✗ argument 1 takes a string, a number or a date, but got null
$.a[null]          // ✗ the key takes a value, but got null
```

No input changes polarity. Each input that this entry names was refused before, and it is
refused now with the new wording.

## 2026-10-18 — fix: a stage body that the document proof cannot read gives an unknown document

`$unwind(null);` crashed the compiler with a `TypeError`, and `validate()` gave a
`SYNTAX_ERROR` at position 0. `$unset([null]);` and `$unset([1]);` crashed in the same
way. The cause was `documentAfter` in
[src/compiler/emit/prove.ts](../../src/compiler/emit/prove.ts). It read the `path` key
of every `$unwind` body, and it read every `$unset` entry as a string.

A `$stage(…)` call is the developer's own MQL (HR2). The row of `$unwind` states no
kind for its body, so the compiler does not refuse `null`. Now the proof gives an
unknown document for a body that it cannot read, and the stage emits as written. The
server judges it. MEASURED on mongod: the server refuses `{ $unwind: null }` and
`{ $unset: [null] }`.

```js
$unwind(null); $.b = $.a;    // → [{ $unwind: null }, { $set: { b: "$a" } }]
```

A table test in [test/compiler-statement.test.ts](../../test/compiler-statement.test.ts)
calls each stage of the registry with a `null` body. Before this change, only `$unwind`
crashed.

No input changes polarity.

## 2026-10-18 — refactor: kinds.ts drops the elements proof of the old constant evaluator

`proofsOfValues` in [src/compiler/kinds.ts](../../src/compiler/kinds.ts) built the proofs
of a list of known values. It left out an element of unknown kind, for example a regular
expression or a Timestamp. So its elements proof claimed fewer kinds than the list holds,
and HR7 forbids that. But no code called the function. The constant evaluator of the JS
twins called it. The MQL interpreter replaced that evaluator (see the entry
"feat: a constant is the value of its lowered MQL: the fold runs an MQL interpreter").
The fold now lowers each constant through the dispatcher. So the live elements proof is
`elementProofOf` in
[src/compiler/emit/type.ts](../../src/compiler/emit/type.ts), and there an element of
unknown kind already makes the proof unknown. The gap was in dead code only.

This change removes `proofsOfValues` and its helper `proofOfValue`, and keeps
`elementsFaultOf` local to its module. It corrects three comments that said the
constant evaluator reads `kinds.ts`. Tests in
[test/compiler-kinds.test.ts](../../test/compiler-kinds.test.ts) now check a list with an
element that the call supplies. The registry does not name the kind of that element.
The tests cover a value, a filter, a stage-written array and the tuple rule.
[docs/specs/types.md](../specs/types.md) states the rule for the `"element"` slot.

```js
// Each `${…}` is a slot of the template tag.
[1, ${/a/}].has("x")                         // → { $in: ["x", [1, /a/]] }   the server decides
[1, ${ts}].max()                             // → { $max: [1, new Timestamp(…)] }
$.a = [1, ${/a/}]; $match($.a === "x");      // → { $match: { a: "x" } }
[1, ${new MinKey()}].has("x")                // ✗ the registry names the kind of MinKey, and no element is a string
```

**No polarity change.** Each input compiled before and compiles now to the same MQL.

## 2026-10-18 — fix!: an arithmetic operator refuses a proven date

The developer decided that `+`, `-`, `*`, `/`, `%` and `**` refuse a date operand. A date
takes the date methods: `.plus()`, `.minus()` and `.diff()`. The `+` row already refused a
proven date, but its `doc` said that it adds to a date. The `-` row stated
`rest: "number-or-date"`, so `$.d.startOf("day") - 1` compiled to `$subtract`. Now the `-`
row states `rest: "number"`. The `doc` of the `-` row names numbers, and the `doc` of the
`+` row names numbers and strings. Comparisons,
`.clamp()` and `.inRange()` on a date do not change.

```js
$.d.startOf("day") - 1              // ✗ the operand is a date; move it with .minus()
$.d.startOf("day").minus(1, "day")  // → { $dateSubtract: { … } }
$.d - 1                             // → { $subtract: ["$d", 1] }   unknown kind: the server decides
```

The `returns` of `+` and `-` stays a number or a date. A field of unknown kind can still
hold a date, and test/compiler-returns-agrees.test.ts measures that answer on mongod.
MEASURED: `$subtract` of two dates one day apart gives the long 86400000. A date minus
1000 is the date one second earlier. A number minus a date is an error.

The refusal of a date in a slot that takes a number now names the date methods. The `hint`
of [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts) reads the refused kinds,
and `kindRefusal` in [src/compiler/emit/errors.ts](../../src/compiler/emit/errors.ts)
calls it. docs/LANGUAGE.md gives the elapsed milliseconds as `.diff(other, "millisecond")`
in place of `-`.

**Polarity change.** `-` with a proven date operand compiled before. JSMQL refuses it now.

## 2026-10-18 — fix!: the query cell of a comparison states the kinds of its value cell

The `filter` cells of `<`, `>`, `<=` and `>=` in
[src/registry/productions.ts](../../src/registry/productions.ts) stated `rest: "any"`, and
their `expr` cells stated `rest: "orderable"`. The `filter` cell of `in` stated
`rest: "any"`, and its `expr` cell stated an element slot and an array slot. So a value
that the value form refuses compiled in a `$match`. The developer decided that the two
cells of one operator state the same kinds. Now each `filter` cell states the kinds of its
`expr` cell.

```js
$.x = null; $match($.x > 1);      // ✗ '>' takes an orderable value, and x is null
$.n = 1; $match($.n in ["a"]);    // ✗ the list holds strings, and n is a number
$.tags = ["a"]; $match($.tags in ["a", "b"]);   // → { $match: { tags: { $in: ["a", "b"] } } }
```

The element slot of `in` needs one more view of a field in a query (SR2). The query tests
each element of an array field against the list. The old rule kept the array as a kind
because the list can be an array, and so refused the last line above. Now `proofsFor` in
[src/compiler/emit/prove.ts](../../src/compiler/emit/prove.ts) gives two more views of an
operand: `asElement` for an element slot, and `whole` for a slot that takes an array.
`faultOf` in [src/compiler/kinds.ts](../../src/compiler/kinds.ts) reads the view that the
slot needs. A kind refusal in a query also lowers the operands first, as the value form
does. So an error inside an operand keeps its own message.

**Polarity change.** A proven value of a kind that the value form refuses compiled in a
query before. JSMQL refuses it now, in `<`, `>`, `<=`, `>=` and `in`.

## 2026-10-18 — feat: a conversion takes a value of its own type

The developer decided that a type conversion to its own type is allowed. Some of these
inputs were refused, and now they compile. `ObjectId($.x)` after `$.x = 0x…` was refused,
because the slot took a string alone. `UUID($.x)` after `$.x = UUID("…")` was refused in the
same way. A constant of the type was refused too: `Long(Long("5"))`, `Int32(Int32(3))`,
`Double(Double(1.5))`, `Decimal128(Decimal128("1.5"))`, `UUID(UUID("…"))`,
`ObjectId(0x…)` and `Date(new Date("…"))`. `String`, `Boolean` and `Number` already took
every value. The numeric types and `Date` already took a proven field of their own type.

The output is the `$to…` operator of the row over the value, as for a runtime value:
`{ $toObjectId: "$x" }`, `{ $toLong: Long("5") }`. The row builds nothing new from a
constant of its own type (`ownValue` in [src/registry/names.ts](../../src/registry/names.ts)).
The constant engine still folds `$toObjectId` and `$toDate` of a constant, as it did before.
MEASURED on mongod 9.0.2: `$toObjectId`, `$toLong`, `$toDouble`, `$toDecimal`, `$toInt`,
`$toUUID`, `$toDate`, `$toString` and `$toBool` each give a value of their own type back,
with the same BSON type and an equal value.

The slot kinds `"objectId"` and `"binData"` are new in
[src/registry/vocabulary.ts](../../src/registry/vocabulary.ts), so that the `ObjectId` and
`UUID` slots can state their own result kind. The compiler has one `number` kind for the
four BSON number types. So `Long(x)` takes any proven number, for example an `Int32`. The
binData kind covers every binary subtype, so `UUID(x)` takes a proven binData that is not a
UUID, and the server decides. A slot takes no new kind except its own type.
`Double(true)` and `Long(new Date(…))` stay refused. See
[docs/LANGUAGE.md](../LANGUAGE.md) § Type Casting and
[docs/specs/bson-types.md](../specs/bson-types.md).

## 2026-10-18 — fix: a null element of a list fits a null needle

The proof of the elements of an array left out a `null` element. `elementProofOf` in
[src/compiler/emit/type.ts](../../src/compiler/emit/type.ts) read only the kinds of the
element, and a `null` is no kind there: the `Type` states it as `absent`. The constant
fold in [src/compiler/kinds.ts](../../src/compiler/kinds.ts) skipped a null element in the
same way. So the `"element"` slot of `.has()`, `in`, `.indexOf()`, `.lastIndexOf()` and
`.without()` refused a `null` needle against a list that holds a null. The refusal also
said that the list holds numbers only, which was false. MEASURED on mongod:
`{ $in: [null, [1, null]] }` gives `true`.

Now an element that can be null adds the kind `null` to the proof of the elements. Only
the element's own presence counts, because a missing array holds no element. The tuple
proof reads the same rule in `itemProofsOf`. So a read that the proof shows is null is a
null position, as a written `null` is. This replaces a patch in
[src/compiler/emit/prove.ts](../../src/compiler/emit/prove.ts) that marked a written
`null` only. A refusal that names the held kinds now names a held null too.

```js
[1, null].has(null)                              // → true   (the fold)
null in [1, $.x]                                 // → { $in: [null, [1, "$x"]] }
$.a = [1, null]; $.r = $.a.has(null);            // → { $in: [null, "$a"] }
[1, 2].has(null)                                 // ✗ null is no number, and no element is null
$.a = [1, null]; $.r = $.a.max();                // ✗ the second position is null, not a number
```

**Polarity change.** A `null` needle against a list that holds a null was refused. It
compiles now, in a value and in a filter. A null position in a stage-written array
compiled before under a row that takes numbers, for example `.max()`. A list with a read
that the proof shows is null did the same. JSMQL refuses both now, as it refuses
`[1, null].max()`.

## 2026-10-18 — feat: a constant is the value of its lowered MQL: the fold runs an MQL interpreter

A constant is an expression whose lowered MQL reads nothing from the document and nothing
from the environment. The fold does not compute with a JavaScript function for each method.
It lowers a closed subtree with the real emitter and gives the MQL to an interpreter. The
developer asked for this because the hand-written JavaScript copy of each method can differ
from its lowering. `.range()` was the example that did not fold. Every method folds as soon
as its lowering exists. The spec is [constant-engine.md](../specs/constant-engine.md).

**What changed.**
- **The definition.** [evaluate.ts](../../src/compiler/passes/evaluate.ts) reads a literal,
  scans the subtree for what never folds (the document, a stream, an `$op(…)` call, a write), and
  substitutes the known constants. It checks that no desugar rule still rewrites the subtree, then
  lowers it and interprets the MQL. The fold writes back every value that it computes.
- **The provided lowering.** `evaluate.ts` cannot import the emitter, so the emitter provides one function
  at load (`provideLowering` in [lower.ts](../../src/compiler/emit/lower.ts)). A lowering that only
  asks for a value skips the checks that refuse MQL which the server rejects (`Site.settling`).
- **The interpreter.** [src/compiler/interpret/](../../src/compiler/interpret/CLAUDE.md) holds one
  rule for each operator that it runs, and a `REFUSED` table with one reason for each operator that it
  knows and does not run. A rule refuses where the server answer is not exactly specified, and the
  expression then stays a runtime expression. A NaN or an infinity is `unspellable`, and the fold
  reports it at the position of the constant.
- **The server-agreement suite.** [compiler-interpret-agrees.test.ts](../../test/compiler-interpret-agrees.test.ts)
  runs a table of cases for each rule on a live `mongod`, and compares the two values. The randomized runs
  reported about 3.5 million comparisons for the core operators, 80 thousand for dates and 110 thousand
  regular-expression patterns. A guard fails the suite when only some of the cases run.
  [compiler-interpret-rows.test.ts](../../test/compiler-interpret-rows.test.ts) fails when an operator
  row has neither a rule nor a refusal.
- **The two copies are deleted.** This change deletes `fold-methods.ts`, `fold-dates.ts` and
  `compiler-fold-rows.test.ts`. An audit corrected the titles of the fold tests, so each title says what its test asserts.
- **The date literal reader.** [date-literal.ts](../../src/compiler/passes/date-literal.ts) reads a date
  that the source spells with literal parts (`new Date("2026-01-01")`, `new Date(0)`,
  `new Date(Date.UTC(2026, 1, 1))`). The date methods then run on the lowered MQL.
- **The emit-phase gates read a literal only.** After the fold, `constantOf` reads a literal, an `Injected`
  node, and a list or a document of them. It never lowers.
- **The `Boolean(x)` fix.** `Boolean(x)` lowers through the new `boolean` service, so it answers `true`
  or `false` as a value. It used the truth test of a condition, which keeps a number as it stands.
- **The `construct` service.** A constructor with a constant argument (`Int32(3)`, `ObjectId("…")`,
  `MinKey()`) builds the live BSON value in its row. The value goes into the MQL as itself, and the
  interpreter passes it through.

**Decisions.**
- **Lazy branches.** The interpreter never evaluates a branch that the answer does not need. The server
  folds a constant branch that nothing takes, and then fails on it. So the two differ on nine cases, which
  `DIVERGE` records with the reason: `$and`, `$or`, `$cond` (two forms), `$ifNull`, `$switch`, `$let`,
  `$map` and `$filter`. The interpreter follows JavaScript here, so a guard such as `d === 0 ? 0 : 1 / d` works.
- **The set mark.** A set operator answers in an order that the server does not specify. A value that an
  operator builds from such an answer, one element at a time, carries a mark. A rule that reads a position
  refuses a marked value, and the suites compare a marked answer as a set.
- **`NumberText`.** A number can print in a form that differs from JavaScript. Its text is a `NumberText`.
  The interpreter knows only that it starts with an optional minus sign and a digit. That is all that the
  finite-number test of a lowering reads. An answer that holds one is a refusal.
- **The regular-expression pattern rules.** The three regular-expression operators run only for a pattern in the
  small syntax that PCRE2 and JavaScript share, and only with no option or with `i`.
- **UTC only.** A date operator runs only when the zone is UTC. The interpreter holds no zone table.
- **Conversions.** `$toInt` runs, because its answer is fully specified. `$toLong`, `$toDouble`, `$toDecimal`
  and `$convert` stay refused, because they change the BSON numeric type.

**Changed results.** Each input below folds at compile time.
- The `.range()` family, such as `(3).range().map(() => 7)`.
- `.intersection()` of two constant arrays.
- `"hello".substr(-3)`.
- `"hello".repeat(-1)`, which gives `""` as the server does, where JavaScript throws.
- `9007199254740992 + 1`. A number past 2^31 is a double on both sides.
- `typeof 1`, which gives the name that `$type` gives.
- `.startOf("week", { startOfWeek: "monday" })`.
- `.diff()` and `.format()` with the zone `"UTC"`.
- `.groupBy()` and `.countBy()` of a constant list.

Each input below changed from folding to refusing.
- [HR7](../LANG_RULES.md) refuses `["a", "b"].has(2)` and the similar methods, because the element is not of the kind that the array holds.
- The compiler refuses `mapKeys(() => …)` with no parameter.

## 2026-10-17 — fix!: a null argument is refused where the slot states a kind

HR7 states three consequences. This entry upholds the third one: JSMQL refuses a `null`
where the slot needs a kind, because `null` is not that kind. Before this change, a
literal `null` passed every slot check. `$.a.slice(null)` compiled to
`{ $slice: [arr, null, …] }`, and the server gave a silent `null`, an empty string, a
bound of `.clamp()` or a runtime error, by method.

The slot check now refuses a `null` from three sources:

- **A written `null`.** `checkType` in
  [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts) returned early for a `null`
  literal. Now it refuses one in every slot that states a kind: a `slotType`, a body
  `keyTypes` key and an `arrayOf` element.
- **A proven `null`.** `Known` in [src/compiler/emit/prove.ts](../../src/compiler/emit/prove.ts)
  gains the member `"null"`. `kindOf` answers it for a proof with no kind, for example
  `let x = null` or a `?.` read of a key that no stage wrote. `kindFits` is false for it,
  so `checkSlots` refuses it. Each reader of `kindOf` that asks for a family reads
  `"null"` as no family. The `kind` service that a cell receives maps `"null"` to
  `"unknown"`.
- **An injected `null`.** A `jsmql.compile` parameter or a template `${…}` value becomes a
  `NullLiteral`, so the call refuses it at call time, as it refuses an injected `"x"`.

`validate()` of a parameterised arrow checked the program with every parameter bound to
`null`. That binding would now refuse a valid arrow such as `({ n }, { $ }) => $.a.slice(n)`.
So [src/index.ts](../../src/index.ts) binds each parameter to a value that no literal spells.
The proof shows no kind for the value. The call still checks the real value.

The message names no alternative for a `null`, because the fix depends on what the
developer meant. A slot that states no kind keeps `null` as a value: `.has(null)`,
`.indexOf(null)`, `??`, `===` and `typeof` are unchanged. The escape hatch is unchanged:
`$sampleRate(null)` emits `{ $sampleRate: null }` by HR2.

**Polarity changes.** Each of these inputs compiled before. JSMQL refuses each one now:
`$.a.slice(null)`, `$.s.charAt(null)`, `$.s.includes(null)`, `$.s.repeat(null)`,
`$.a.chunk(null)`, `$.d.plus(null, "day")`, `$.d.set({ year: null })`, `$.o.pick([null])`,
`$$.take(null);`, `let x = null; $.r = $.a.slice(x);`, and the same slots with an injected
`null`. A slot that states no kind still takes `null`, for example the slots of `.at()`,
`.round()` and `.clamp()`. The operator productions state no kinds yet.

Series A of the constant engine on branch `claude/constant-value-engine-7b0d73` owns
the other two consequences of HR7. They are the `===` of two proven different kinds, and
the membership test of the wrong kind. Series A also makes every slot state a kind, with an
audit test over every row. That work stays open.

## 2026-10-17 — feat!: `.toString()` is the bare `$toString`

## 2026-10-17 — docs: HR7 — JSMQL refuses a value of the wrong kind

[docs/LANG_RULES.md](../LANG_RULES.md) states a new hard rule, HR7. Each method, operator
and argument slot states the kind of value that it takes. When the compiler can prove that a
value has another kind, it refuses the program, even when the server accepts the MQL. A
value of unknown kind passes, and the server decides. The reason is the design goal of the
language: JSMQL is JavaScript syntax with strict kinds. A JavaScript developer expects
`"a" + 1` to join text, and never expects `$add`. The escape hatch `$op(…)` is the one way
to the permissive behaviour of MongoDB, by HR2. The rule "one capability gets one spelling"
is unchanged. The JavaScript form checks the kind. The `$op(…)` form passes the value as
written. [docs/LANGUAGE.md](../LANGUAGE.md) points at the rule from the section on a
method chained on the wrong type.

```
[1, "a"].max()        ✗ .max() takes numbers
$max(1, "a")          → { $max: [1, "a"] }      as written, by HR2
$.str + 1             → { $add: ["$str", 1] }   unknown kind: the server decides
$.str.trim() + 1      ✗ .trim() gives a string
```

The rule has three consequences. A `===` between two proven different kinds is always
false, so the compiler refuses it. The compiler refuses a membership test of the wrong
kind for the same reason, for example `.has(1)` on a proven array of strings. The compiler
refuses a literal `null` where the slot needs a kind, because `null` is not that kind.

**Open work.** The compiler does not uphold HR7 yet. The refused lines above compile
today. The conformance engine is on a separate branch:
`claude/constant-value-engine-7b0d73`. This change edits documentation only. It adds no
DEFERRED row, because that branch already plans the work.

## 2026-10-17 — feat: a shorter null test, and `$cond` in its array form

The developer asked for the shortest MQL of `?.`. Two shapes in every program get
shorter. The null test of `?.` and of a string method is `{ $lte: [x, null] }` in place
of `{ $eq: [{ $ifNull: [x, null] }, null] }`. Its negation in the JavaScript truthiness
check is `{ $gt: [x, null] }`. Null sorts below every other value but `MinKey`, so one
comparison covers missing and null. The mongod server gave the same answer for both
tests on a missing value, `null`, `0`, `""`, `false`, `[]` and `{}`. Only a `MinKey` value
reads as null now, and the developer accepts that.

object `{ if, then, else }`. The developer's own `$cond(…)` call keeps the object form
that HR2 gives it, because it is the developer's MQL.

```
$.s?.trim()     → { $cond: [{ $lte: ["$s", null] }, null, { $trim: { input: "$s" } }] }
$.a ? 1 : 2     → { $cond: [{ $and: [{ $gt: ["$a", null] }, { $ne: ["$a", false] }, …] }, 1, 2] }
```

## 2026-10-17 — feat: `.random()` is lodash's `_.random` on a number

`x.random()` gives a number from 0 to `x`. `x.random(y)` gives a number between `x` and
`y`. Both match lodash's `_.random(x)` and `_.random(x, y)`. The bounds swap when the first is larger.
lodash gives a whole number, both ends included, when both bounds are whole, and a
fractional number otherwise. The developer picked that rule, tested at run time. Two constant
bounds decide the form at compile time. For bounds from a document, the MQL holds a `$let` of

as lodash reads it, so the row states `nullReceiverAs: 0`.

```
(1.5).random(2)     → { $add: [1.5, { $multiply: [{ $rand: {} }, 0.5] }] }
$.a.random($.b)     → { $let: { vars: { jsmqlLo: { $min: […] }, jsmqlHi: { $max: […] } }, in: { $cond: … } } }
```

## 2026-10-17 — feat!: the receiver methods replace the `Object` statics

JSMQL had two spellings for each object reader: the JavaScript static and the method of
the receiver. The developer's rule is "one capability gets one spelling, and the shorter
spelling wins". The method is shorter in each case, so `Object.keys`, `Object.values`,
`Object.entries`, `Object.fromEntries` and `Object.assign` are no longer JSMQL names.
They still parse, and the `Object` cell of each row refuses the call and names the
method, as `Object.groupBy` does. The `Object` root row stays, because the refusal
needs the name to parse. A suggestion for a misspelled static never names a refused
static now (`lowersOn` in [src/compiler/rows.ts](../../src/compiler/rows.ts)).

```
Object.keys($.doc)           ✗ write $.doc.keys()
Object.assign(...$.docs)     ✗ write ({}).assign(...$.docs)
Object.assign($.f, $.x);     ✗ write $.f = { ...$.f, ...$.x };
({}).assign(...$.docs)       → { $mergeObjects: "$docs" }
({}).assign($.o)             → { $mergeObjects: ["$o"] }
$.a.assign(...$.docs)        → { $mergeObjects: { $concatArrays: [["$a"], { $ifNull: ["$docs", []] }] } }
$.o.keys()                   → { $map: { input: { $objectToArray: { $ifNull: ["$o", {}] } }, in: "$$this.k" } }
$.p.fromEntries()            → { $arrayToObject: { $map: { input: { $ifNull: ["$p", []] }, in: [{ $toString: { $first: "$$this" } }, { $arrayElemAt: ["$$this", 1] }] } } }
```

`.assign()` reads a spread argument as a list of sources and a plain argument as one
source. Before, `({}).assign(...$.docs)` emitted `{ $mergeObjects: [{}, "$docs"] }`, and
the server rejects that when `docs` is an array. An empty receiver is now dropped.
After a real receiver, a spread list takes the HR5 guard of the array literal. Without
it, the server answers `{}` for `{ $mergeObjects: { $concatArrays: [["$o"], "$nope"] } }`,
so the receiver is lost. The mongod server also merges `{ $mergeObjects: ["$docs"] }`
as one list, so `["$o"]` and `"$o"` give the same answer for one plain source.

`.assign()` writes nothing in place, so the desugar rule that turned
`Object.assign(t, …);` into a write is gone, with the `mutatesArgumentAt` row fact.
lodash's `_.assign` writes its target, so a lone `$.p.assign(…)` or `r.assign(…);` is
still a statement, and the statement cell refuses it and names the write back.
`.keys()`, `.values()`, `.entries()`, `.toPairs()` and `.fromEntries()` read `$$this`
in place of a minted name, because each `in` body is fixed compiler text. The fold
now folds the method forms on a constant: `({ a: 1 }).keys()` is `["a"]`.

## 2026-10-17 — docs: HR5 states the number rule
