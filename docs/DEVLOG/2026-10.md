## 2026-10-18 — feat!: every slot refuses null unless null is data there

HR7 refuses a `null` where the slot expects a value that is not null. The entry "fix!: a
null argument is refused where the slot states a kind" applied this rule only to a slot
with a stated kind. A slot with no stated kind still passed `null` to the server.
`$.n.round(null)`, `$.a.at(null)` and `$.n.clamp(null, 5)` compiled. `$.a.sumBy(null)`
gave an internal error. `Number(null)` and `String(null)` compiled too, because a global
call never ran the slot check.

Now every slot and every option key refuses `null`. This covers a written `null`, an
injected `null` and a value that the proof shows is null. A row states the slots where
`null` is data with the new `Arity` field `takesNull`, a list of slots or `"every"`.
Examples are the value of `.has()`, the items of `.concat()` and the seed of
`.reduce()`. The productions `===`, `!==`, `==`, `!=`, `??`, `?:`, `!`, `typeof` and `in`
state `takesNull: "every"`.

Four more changes serve the rule:

- `checkSlots` in [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts) takes a
  `kindOf` function in place of a list of kinds. So it also reads the proof of an option
  key and of an element of a list.
- A global call (`Number(x)`, `assert(…)`) and a static call (`Date.UTC(…)`) now run the
  slot check. The message spells them `Number()` and `Date.UTC()`.
- A fold does not fold a call with a `null` where the row refuses one (`takesNullAt` in
  [src/compiler/rows.ts](../../src/compiler/rows.ts)). So `String(null)` reaches the check.
- The slots of a set of rows that take a number, a string or an array state their kind,
  so the refusal names that kind. For example, the precision of `.round()` takes an integer, and the other array
  of `.xor()` takes an array. A slot with no single kind, for example a callback, names
  "a value".

**Polarity changes.** Each of these inputs compiled before. JSMQL refuses each one now:

- `null` in a slot with no stated kind, for example `$.n.round(null)`, `$.a.at(null)`,
  `$.a.join(null)` and `$.a.xor(null)`
- `Number(null)`, `String(null)`, `Boolean(null)` and `Date.UTC(null)`
- `null` in an option key, for example `{ startOfWeek: null }`
- `assert(cond, 5)`, because the message of `assert()` takes a string

## 2026-10-18 — fix: .matchAll() takes a string pattern again

The entry "feat!: .range() and the unit, match and test slots state their slot type" gave
the pattern slot of `.matchAll()` the kind "a regular expression". The kind refused
`$.s.matchAll("a.")`, a useful spelling that JavaScript accepts and that compiled before.
Now the slot takes a string or a regular expression, as the slot of `.match()` does. A
regular expression still needs the `g` flag.

```js
$.s.matchAll("a.")    // → { $cond: [{ $lte: ["$s", null] }, null, { $regexFindAll: { input: "$s", regex: "a." } }] }
$.s.matchAll(5)       // ✗ .matchAll() takes a string or a regular expression
```

**Polarity change.** `$.s.matchAll("x")` compiles again.

## 2026-10-18 — fix: a refused injected value points at its name

A `jsmql.compile` parameter and a template `${…}` value go into the tree through
[src/compiler/passes/inject.ts](../../src/compiler/passes/inject.ts). The pass spelled each
value once, at position 0. It moved only an `Injected` node, for example a Date, to the
position of the reference. A value that the source can spell, for example `null`, `"x"` or a
number, kept position 0. So the refusal of such a value had `.pos` 0, and a tool could not
underline the name.

Now `inject()` spells each value at the position of each reference, also inside a list or a
document. A `const` prelude still keeps the positions of its own source expression, because
`replaceIdents` keeps its old rule.

```js
jsmql.expr.compile(({ start }, { $ }) => $.a.slice(start))({ start: null })
// ✗ .pos is the offset of `start` in the arrow's source. It was 0.
jsmql.validate`$.a.slice(${null})`
// ✗ .pos is 10, the offset of the slot. It was 0.
```

No input changes polarity.

## 2026-10-17 — feat!: .range() and the unit, match and test slots state their slot type

Some slots in [src/registry/names.ts](../../src/registry/names.ts) had a rule that implies
a kind, but no `slotType`. A rule of this type is, for example, `integer`, `slotEnums`,
`regexFlag` or `nonEmpty`. Without the `slotType`, the slot let a value of another kind
through, and `null` too. Now each one states its kind:

- `.range()` and `.rangeRight()`, slots 1 and 2: an integer
- the unit of `.plus()`, `.minus()`, `.diff()`, `.isSame()`, `.isBefore()` and `.isAfter()`
  (slot 2), and of `.startOf()` and `.endOf()` (slot 1): a string
- the stream link `.aggregate()`, slot 1: an array of stages
- `.matchAll()`, slot 1: a regular expression

Two more rows implied a kind and stated none. `.match()` takes a string or a regular
expression, on its value cell and on its filter cell. `/re/.test(s)` takes a string as its
input. Before this change, `$.s.test(null)` crashed `jsmql.stringify` with an `undefined`
value. Now the slot check refuses the call with a message.

A script over `NAMES` finds a slot with such a rule and no `slotType`. The script lists no
slot now.

**Polarity changes.** Each of these inputs compiled before. JSMQL refuses each one now:

- `.range("x")`, and a `null` in a slot of `.range()`
- a unit of another kind, for example `$.d.plus(1, 5)`
- `$.s.matchAll("x")`, because the slot takes a regular expression, as the docs say
- `$.s.match(5)`, `/a/.test(5)`, and `null` in each of these slots
- `$$.aggregate(null);`

## 2026-10-17 — feat!: each operator states the kinds of its operands

HR7 says that each method, operator and argument slot states the kind of value it takes.
Before this change, no operator production in
[src/registry/productions.ts](../../src/registry/productions.ts) stated a kind. So
`$.n + null`, `$.n > null` and `$.a[null]` passed to the server. Now each operator states
the kinds of its operands, on its `expr` cell and on its `filter` cell where it has both:

| Operator | Kind of each operand |
|---|---|
| `+` | a number, a string or a date |
| `-` | a number or a date |
| `*`, `/`, `%`, `**`, `-x` | a number |
| `~`, `\|`, `&`, `^` | an integer |
| `<`, `>`, `<=`, `>=` | a value of any kind |
| `x[i]` | a key of any kind |
| `===`, `!==`, `==`, `!=`, `??`, `?:`, `&&`, `\|\|`, `!`, `typeof`, `in` | nothing, because the operator takes `null` there |

Four facts in [src/registry/vocabulary.ts](../../src/registry/vocabulary.ts) serve this.
`ArgType` gains `"any"`, a slot of every kind but never `null`. It also gains `"regex"`, a
slot that a regex literal fills. `Arity` gains `rest`, the kind of each operand of a
flattened chain beyond the stated slots. `inCode(file, args)` lets the `+` road and the
`x[i]` road state their rule, and each road runs `checkSlots` with it.

The plan for this change gave `x[i]` the kinds "an integer or a string". The code turns a
key of any other kind into its string, as JavaScript does for `o[k]`. The collaborative
filtering example in [test/realistic.test.ts](../../test/realistic.test.ts) reads
`counts[id]` with an ObjectId key. So `x[i]` states `"any"`, and it refuses only `null`.

A proven `null` operand now lowers before its refusal. A read of a field that no stage wrote
has its own refusal, and that refusal names the cause:
`$group({ _id: $.k, n: $sum(1) }); $match($.total > 5);` still says that the document has no
field `total`.

**Polarity changes.** Each of these inputs compiled before. JSMQL refuses each one now:

- a `null` operand of an operator in the table, for example `$.n + null` and `$.n > null`,
  in a filter and in a value
- `$.a[null]`
- an operand of a proven wrong kind, for example `$.s.trim() * 2`
- a fraction in a bitwise operator, for example `$.n | 1.5`
- `$.a === $.b & $.c`, because `&` then takes a boolean

## 2026-10-17 — fix!: a null argument is refused where the slot states a kind

HR7 states three consequences. This entry upholds the third one: JSMQL refuses a `null`
where the slot needs a kind, because `null` is not that kind. Before this change, a
literal `null` passed every slot check. `$.a.slice(null)` compiled to
`{ $slice: [arr, null, …] }`, and the server gave a silent `null`, an empty string, a
bound of `.clamp()` or a runtime error, by method.

The slot check now refuses a `null` from three sources:

- **A written `null`.** `checkType` in
  [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts) returned early for a `null`
  literal. Now it refuses one in every slot that states a kind: a `slotType`, a body
  `keyTypes` key and an `arrayOf` element.
- **A proven `null`.** `Known` in [src/compiler/emit/prove.ts](../../src/compiler/emit/prove.ts)
  gains the member `"null"`. `kindOf` answers it for a proof with no kind, for example
  `let x = null` or a `?.` read of a key that no stage wrote. `kindFits` is false for it,
  so `checkSlots` refuses it. Each reader of `kindOf` that asks for a family reads
  `"null"` as no family. The `kind` service that a cell receives maps `"null"` to
  `"unknown"`.
- **An injected `null`.** A `jsmql.compile` parameter or a template `${…}` value becomes a
  `NullLiteral`, so the call refuses it at call time, as it refuses an injected `"x"`.

`validate()` of a parameterised arrow checked the program with every parameter bound to
`null`. That binding would now refuse a valid arrow such as `({ n }, { $ }) => $.a.slice(n)`.
So [src/index.ts](../../src/index.ts) binds each parameter to a value that no literal spells.
The proof shows no kind for the value. The call still checks the real value.

The message names no alternative for a `null`, because the fix depends on what the
developer meant. A slot that states no kind keeps `null` as a value: `.has(null)`,
`.indexOf(null)`, `??`, `===` and `typeof` are unchanged. The escape hatch is unchanged:
`$sampleRate(null)` emits `{ $sampleRate: null }` by HR2.

**Polarity changes.** Each of these inputs compiled before. JSMQL refuses each one now:
`$.a.slice(null)`, `$.s.charAt(null)`, `$.s.includes(null)`, `$.s.repeat(null)`,
`$.a.chunk(null)`, `$.d.plus(null, "day")`, `$.d.set({ year: null })`, `$.o.pick([null])`,
`$$.take(null);`, `let x = null; $.r = $.a.slice(x);`, and the same slots with an injected
`null`. A slot that states no kind still takes `null`, for example the slots of `.at()`,
`.round()` and `.clamp()`. The operator productions state no kinds yet.

Series A of the constant engine on branch `claude/constant-value-engine-7b0d73` owns
the other two consequences of HR7. They are the `===` of two proven different kinds, and
the membership test of the wrong kind. Series A also makes every slot state a kind, with an
audit test over every row. That work stays open.

## 2026-10-17 — fix: `.indexOfSubstring()` takes an integer position

The developer stated how HR7 applies to a number slot. JSMQL refuses a fraction where the
slot takes an integer, and a string where the slot takes a number. The entry
[feat: `.indexOfSubstring()` finds a substring](#2026-10-17--feat-indexofsubstring-finds-a-substring)

states `slotType: { 0: "string", 1: "int" }`, and the compiler refuses a fractional or a

$.s.indexOfSubstring("b", 1.7)    ✗ position takes an integer (was { $indexOfCP: ["$s", "b", 1] })

through `$max`, as `undefined` does in JavaScript. A fractional run-time position stops the

## 2026-10-17 — feat!: `.indexOf()` is an array method only

The developer decided that `.indexOf()` reads an array only. A string takes
`.indexOfSubstring()`. Nothing guesses the receiver now. The compiler does not pick the
operator from the type of the argument. The MQL does not test the type with a `$switch`
when it runs. HR5 fact 1 in docs/LANG_RULES.md states the new rule.

```
$.a.indexOf(2)              → { $indexOfArray: [{ $ifNull: ["$a", []] }, 2] }
$.s.indexOf("b")            → { $indexOfArray: [{ $ifNull: ["$s", []] }, "b"] }   (was a $switch on $type)
$.s.trim().indexOf("b")     ✗ the refusal names .indexOfSubstring()
"abc".indexOf("b")          ✗ (was the fold 1)
$.s.trim().lastIndexOf("b") ✗ the refusal names .indexOfSubstring(), not $op($indexOfCP, …)
```

The polarity changes: `.indexOf()` on a proven string is refused, and the fold of a
string `.indexOf()` is gone. `.lastIndexOf()` is also a one-family row now. Its
`sibling` sentence replaces the per-family refusal, and its array output is the same.

## 2026-10-17 — docs: HR7 — JSMQL refuses a value of the wrong kind

[docs/LANG_RULES.md](../LANG_RULES.md) states a new hard rule, HR7. Each method, operator
and argument slot states the kind of value that it takes. When the compiler can prove that a
value has another kind, it refuses the program, even when the server accepts the MQL. A
value of unknown kind passes, and the server decides. The reason is the design goal of the
language: JSMQL is JavaScript syntax with strict kinds. A JavaScript developer expects
`"a" + 1` to join text, and never expects `$add`. The escape hatch `$op(…)` is the one way
to the permissive behaviour of MongoDB, by HR2. The rule "one capability gets one spelling"
is unchanged. The JavaScript form checks the kind. The `$op(…)` form passes the value as
written. [docs/LANGUAGE.md](../LANGUAGE.md) points at the rule from the section on a
method chained on the wrong type.

```
[1, "a"].max()        ✗ .max() takes numbers
$max(1, "a")          → { $max: [1, "a"] }      as written, by HR2
$.str + 1             → { $add: ["$str", 1] }   unknown kind: the server decides
$.str.trim() + 1      ✗ .trim() gives a string
```

The rule has three consequences. A `===` between two proven different kinds is always
false, so the compiler refuses it. The compiler refuses a membership test of the wrong
kind for the same reason, for example `.has(1)` on a proven array of strings. The compiler
refuses a literal `null` where the slot needs a kind, because `null` is not that kind.

**Open work.** The compiler does not uphold HR7 yet. The refused lines above compile
today. The conformance engine is on a separate branch:
`claude/constant-value-engine-7b0d73`. This change edits documentation only. It adds no
DEFERRED row, because that branch already plans the work.
