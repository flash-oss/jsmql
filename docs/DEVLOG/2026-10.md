## 2026-10-17 — refactor: remove the run-time type dispatch

After the entry
[feat!: `.indexOf()` is an array method only](#2026-10-17--feat-indexof-is-an-array-method-only),
no row lowers on two field families. The developer decided to remove the dispatch code. An
unproven receiver is the one field family that the row lowers on. No query tests the type
of the receiver.

The change removes these parts:

- the `$switch` of the dispatch
- the step where a proven argument kind picks a branch
- the `$type` guards and their measurement on mongod
- the row fields `uncertain` and `alsoTypes`

A test in
[test/compiler-select.test.ts](../../test/compiler-select.test.ts) refuses a row that
lowers on two field families. The emitted MQL does not change.

## 2026-10-17 — fix: one wording for a value of the wrong kind

Three checks refused a value of the wrong kind. Each one worded the refusal in its own
way. The literal check named a method without its dot. The proof check named it as the
source spells it. The integer check of `.range()` had a third message. For a fraction in
an integer slot, the literal check called the value a number. That wording was correct,
but it did not help.

One function in [src/compiler/emit/check.ts](../../src/compiler/emit/check.ts) now builds
the refusal for all three checks. The message names the method as the source spells it,
the kind that the slot takes, and the kind of the value. A fraction in an integer slot is
a fraction. The message names `.ceil()` and `.floor()`.

```
$.s.includes(1)              ✗ the literal check and the proof check give one sentence
$.s.includes($.s.length())   ✗ the same sentence
$.a.slice(1.5)               ✗ the value is a fraction; round it with .ceil() or .floor()
(0.5).range(3)               ✗ the same sentence as for .slice(1.5)
```

## 2026-10-17 — fix: a string method refuses an argument of the wrong kind

The developer stated that HR7 holds for each argument slot. No string method row stated
the kind of its arguments, so the compiler passed any literal to the server. Each row now
states `slotType`. An index, a count or a length takes an integer. A search string, a
separator, a replacement or a pad string takes a string.

```
$.s.substring(-1.5)          ✗ start takes an integer
$.s.repeat(2.5)              ✗ count takes an integer   (was { $range: [0, 2.5] } in a $reduce)
$.s.charAt("1")              ✗ index takes an integer
$.s.padStart(3, 0)           ✗ the pad string takes a string
$.s.includes(1)              ✗ the search string takes a string
$.s.includes($.s.length())   ✗ the compiler proves a number
```

A measurement on mongod shows that the server refuses these values. `$substrCP` refuses a
fractional or a string index. `$range` refuses a fractional or a string count.
`$indexOfCP`, `$split` and `$replaceOne` refuse a number where they read a string. So most
of the old MQL failed on the server. The old MQL also broke HR3.

A literal `null` still satisfies each `slotType`, for example in `$.a.slice(null)`. HR7
refuses a literal `null` in each slot. The open work in the entry
[docs: HR7 — JSMQL refuses a value of the wrong kind](#2026-10-17--docs-hr7--jsmql-refuses-a-value-of-the-wrong-kind)
addresses this problem.

## 2026-10-17 — fix: `.indexOfSubstring()` takes an integer position

The developer stated how HR7 applies to a number slot. JSMQL refuses a fraction where the
slot takes an integer, and a string where the slot takes a number. The entry
[feat: `.indexOfSubstring()` finds a substring](#2026-10-17--feat-indexofsubstring-finds-a-substring)
below says that a constant start reads as its integer part. This claim is wrong. The row now
states `slotType: { 0: "string", 1: "int" }`, and the compiler refuses a fractional or a
string position. A negative integer still reads as 0, as in JavaScript.

```
$.s.indexOfSubstring("b", 1.7)    ✗ position takes an integer (was { $indexOfCP: ["$s", "b", 1] })
$.s.indexOfSubstring("b", "2")    ✗ position takes an integer (was { $max: [0, "2"] })
$.s.indexOfSubstring("b", -3)     → { $indexOfCP: ["$s", "b"] }
$.s.indexOfSubstring("b", $.n)    → { $indexOfCP: ["$s", "b", { $max: [0, "$n"] }] }
```

A measurement on mongod shows this: a missing or `null` run-time position reads as 0
through `$max`, as `undefined` does in JavaScript. A fractional run-time position stops the
query.

## 2026-10-17 — feat!: `.indexOf()` is an array method only

The developer decided that `.indexOf()` reads an array only. A string takes
`.indexOfSubstring()`. Nothing guesses the receiver now. The compiler does not pick the
operator from the type of the argument. The MQL does not test the type with a `$switch`
when it runs. HR5 fact 1 in docs/LANG_RULES.md states the new rule.

```
$.a.indexOf(2)              → { $indexOfArray: [{ $ifNull: ["$a", []] }, 2] }
$.s.indexOf("b")            → { $indexOfArray: [{ $ifNull: ["$s", []] }, "b"] }   (was a $switch on $type)
$.s.trim().indexOf("b")     ✗ the refusal names .indexOfSubstring()
"abc".indexOf("b")          ✗ (was the fold 1)
$.s.trim().lastIndexOf("b") ✗ the refusal names .indexOfSubstring(), not $op($indexOfCP, …)
```

The polarity changes: `.indexOf()` on a proven string is refused, and the fold of a
string `.indexOf()` is gone. `.lastIndexOf()` is also a one-family row now. Its
`sibling` sentence replaces the per-family refusal, and its array output is the same.

No row lowers two field families now. So no row reaches the run-time `$type`
dispatch in `src/compiler/emit/select.ts`. The step where a proven argument kind picks a
branch has no user either. The tests that drove the dispatch through `.indexOf()` are
removed, and the specs use examples that are still true. The dispatch code stays, and
the developer decides about it.

## 2026-10-17 — feat: `.indexOfSubstring()` finds a substring

A string takes a new method, `.indexOfSubstring(searchString[, position])`. Its API is the
API of JavaScript's `String.prototype.indexOf`. JavaScript has no other name for it, so the
name is JSMQL's own (SR3). The method lowers to `$indexOfCP`. The developer chose this name,
because `.indexOf()` becomes an array method only.

```
$.s.indexOfSubstring("b")         → { $indexOfCP: ["$s", "b"] }
$.s.indexOfSubstring("b", 2)      → { $indexOfCP: ["$s", "b", 2] }
$.s.indexOfSubstring("b", -3)     → { $indexOfCP: ["$s", "b"] }
$.s.indexOfSubstring("b", $.n)    → { $indexOfCP: ["$s", "b", { $max: [0, "$n"] }] }
"abc".indexOfSubstring("b")       → 1
```

These facts come from mongod:

- `$indexOfCP` gives `null` for a missing or `null` receiver. So the row states
  `passesNull`, and a dot or a `?.` adds no `$cond`.
- `$indexOfCP` refuses a negative, a fractional and a `null` start. JavaScript reads a
  constant start as its integer part, at least 0. The row writes that value. The row drops
  a start of 0. A run-time start takes `{ $max: [0, …] }`, as `.substring()` does.
- An empty search string at a start at or past the end gives -1, unless the start is 0.
  JavaScript gives the length there. The fold gives the server's answer, and
  docs/LANGUAGE.md states the difference.

## 2026-10-17 — feat!: `.toString()` under a dot gives `""` for a missing value

The developer decided that `.toString()` follows lodash's `_.toString()`. Under a dot, a
missing or `null` receiver gives `""`. After a `?.`, it gives `null`, by HR5. The row
states `nullReceiverAs: ""`, and the cell adds the `$ifNull` only where the proof shows
that the receiver can be absent. The developer asked for this: an `$ifNull` only where it
is necessary. `$._id.toString()` keeps the `$ifNull`, because `_id` can be `null`, for
example after a `$group`.

```
$.n.toString()             → { $toString: { $ifNull: ["$n", ""] } }       → "" for {}
$.n?.toString()            → { $toString: "$n" }                          → null for {}
(5).toString()             → { $toString: 5 }
$.a.size().toString()      → { $toString: { $size: { $ifNull: ["$a", []] } } }
$.n.toString().trim()      → { $trim: { input: { $toString: { $ifNull: ["$n", ""] } } } }
$.s.split(",").toString()  → { $toString: { $ifNull: [{ $split: ["$s", ","] }, ""] } }
```

The `NullAnswer` type refused a row that states both `passesNull` and `nullReceiverAs`.
That rule was too strict, because the two facts apply to different accessors.
`passesNull` applies to the `?.`, where the proof shows the receiver there and the cell
emits the bare operator. `nullReceiverAs` applies to the dot. So the type is gone. The
server tables in [test/compiler-methods.test.ts](../../test/compiler-methods.test.ts)
measure each claim.

A row that states `nullReceiverAs` also takes no `[]` or `{}` wrap from HR5. Without this
rule, `$.s.split(",").toString()` gave `"[]"` for a missing `s`.
[HR5](../LANG_RULES.md) states the `""` answer.

## 2026-10-17 — feat!: `.toString()` is the bare `$toString`

`.toString()` lowers to `{ $toString: x }` on every receiver. The lowering emits no `$let`
and no `$isArray` dispatch. So an array gives MongoDB's text, not JavaScript's text. The
developer chose MongoDB's own conversion over an emulation of JavaScript. `.join()` gives
JavaScript's text for an array. The row states `passesNull`, because `$toString` gives null
for a missing value. So `$.x?.toString()` needs no `$cond` test.

```
$.n.toString()             → { $toString: "$n" }
$.x?.toString()            → { $toString: "$x" }
$.tags.uniq().toString()   → { $toString: { $setUnion: { $ifNull: ["$tags", []] } } }
[1, 2].toString()          → { $toString: [[1, 2]] }
/a+/gsi.toString()         → "/a+/is"
```

**Breaking.** On mongod 9.0.2, `$toString` of `[1, [2, 3]]` is `"[1,[2,3]]"`. The old
lowering gave `"1,2,3"`. A date, a document and a missing value also give MongoDB's answer.
[docs/LANGUAGE.md](../LANGUAGE.md) states each difference. An array literal goes in a
one-element list, because `$toString` takes one operand. A regex literal has no value of
its own. The cell writes the text that `$toString` gives for the BSON regex. Before, the
cell emitted the internal node of the regex. Some comments said that `$toString` fails on an
array. That statement was wrong, and the comments now give the measured text.

## 2026-10-17 — docs: HR7 — JSMQL refuses a value of the wrong kind

[docs/LANG_RULES.md](../LANG_RULES.md) states a new hard rule, HR7. Each method, operator
and argument slot states the kind of value that it takes. When the compiler can prove that a
value has another kind, it refuses the program, even when the server accepts the MQL. A
value of unknown kind passes, and the server decides. The reason is the design goal of the
language: JSMQL is JavaScript syntax with strict kinds. A JavaScript developer expects
`"a" + 1` to join text, and never expects `$add`. The escape hatch `$op(…)` is the one way
to the permissive behaviour of MongoDB, by HR2. The rule "one capability gets one spelling"
is unchanged. The JavaScript form checks the kind. The `$op(…)` form passes the value as
written. [docs/LANGUAGE.md](../LANGUAGE.md) points at the rule from the section on a
method chained on the wrong type.

```
[1, "a"].max()        ✗ .max() takes numbers
$max(1, "a")          → { $max: [1, "a"] }      as written, by HR2
$.str + 1             → { $add: ["$str", 1] }   unknown kind: the server decides
$.str.trim() + 1      ✗ .trim() gives a string
```

The rule has three consequences. A `===` between two proven different kinds is always
false, so the compiler refuses it. The compiler refuses a membership test of the wrong
kind for the same reason, for example `.has(1)` on a proven array of strings. The compiler
refuses a literal `null` where the slot needs a kind, because `null` is not that kind.

**Open work.** The compiler does not uphold HR7 yet. The refused lines above compile
today. The conformance engine is on a separate branch:
`claude/constant-value-engine-7b0d73`. This change edits documentation only. It adds no
DEFERRED row, because that branch already plans the work.

## 2026-10-17 — feat: a `?.` read takes no `$ifNull` where the consumer passes null

A `?.` read with no call after it is `{ $ifNull: [x, null] }`, so a missing value reads
as `null`. Many consumers give the same answer for missing and for `null`, and the wrap
adds nothing there. The productions of `+` on numbers, `-`, `*`, `/`, `%`, `**`, `-x` and
`??` now state `passesNull`. A test in
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) measures each one on
mongod. `== null`, `!= null` and every truth test read the operand the same way.
`== null` is now the short null test itself:

```
$.b?.c ** 2       → { $pow: ["$b.c", 2] }                 (was { $pow: [{ $ifNull: ["$b.c", null] }, 2] })
$.b?.c ?? 0       → { $ifNull: ["$b.c", 0] }
$.b?.c == null    → { $lte: ["$b.c", null] }              (was a $type test against "null" and "missing")
$.b?.c ? 1 : 2    → { $cond: [{ $and: [{ $gt: ["$b.c", null] }, …] }, 1, 2] }
$.b?.c === 1      → { $eq: [{ $ifNull: ["$b.c", null] }, 1] }   (kept: $eq tells missing from null)
```

The comparisons keep the wrap, because `{ $eq: ["$nope", null] }` is false and
`{ $eq: [null, null] }` is true. The `.join()` element test uses the short null test too.

## 2026-10-17 — feat: a shorter null test, and `$cond` in its array form

The developer asked for the shortest MQL of `?.`. Two shapes in every program get
shorter. The null test of `?.` and of a string method is `{ $lte: [x, null] }` in place
of `{ $eq: [{ $ifNull: [x, null] }, null] }`. Its negation in the JavaScript truthiness
check is `{ $gt: [x, null] }`. Null sorts below every other value but `MinKey`, so one
comparison covers missing and null. The mongod server gave the same answer for both
tests on a missing value, `null`, `0`, `""`, `false`, `[]` and `{}`. Only a `MinKey` value
reads as null now, and the developer accepts that.

The compiler writes each `$cond` in the array form `[if, then, else]`, in place of the
object `{ if, then, else }`. The developer's own `$cond(…)` call keeps the object form
that HR2 gives it, because it is the developer's MQL.

```
$.s?.trim()     → { $cond: [{ $lte: ["$s", null] }, null, { $trim: { input: "$s" } }] }
$.a ? 1 : 2     → { $cond: [{ $and: [{ $gt: ["$a", null] }, { $ne: ["$a", false] }, …] }, 1, 2] }
```

## 2026-10-17 — feat: `.random()` is lodash's `_.random` on a number

`x.random()` gives a number from 0 to `x`. `x.random(y)` gives a number between `x` and
`y`. Both match lodash's `_.random(x)` and `_.random(x, y)`. The bounds swap when the first is larger.
lodash gives a whole number, both ends included, when both bounds are whole, and a
fractional number otherwise. The developer picked that rule, tested at run time. Two constant
bounds decide the form at compile time. For bounds from a document, the MQL holds a `$let` of
the two ends, and the server runs a `$cond` whole-number test. A missing bound reads as `0`,
as lodash reads it, so the row states `nullReceiverAs: 0`.

```
(1).random(6)       → { $add: [1, { $floor: { $multiply: [{ $rand: {} }, 6] } }] }
(5).random()        → { $floor: { $multiply: [{ $rand: {} }, 6] } }
(1.5).random(2)     → { $add: [1.5, { $multiply: [{ $rand: {} }, 0.5] }] }
$.a.random($.b)     → { $let: { vars: { jsmqlLo: { $min: […] }, jsmqlHi: { $max: […] } }, in: { $cond: … } } }
```

A test in [test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) runs each
form 400 times on mongod. It checks the range, both whole ends, and the whole or
fractional answer. `Math.random()` stays `{ $rand: {} }`. JSMQL does not take lodash's
third argument, `floating`.

## 2026-10-17 — feat!: the number methods replace the `Math` members that take a value

The rule "one capability gets one spelling, and the shorter spelling wins" also covers
`Math`. Each member that takes a value now lives on the number receiver. The `Math`
cell of each row refuses the static and names the method. `Math.pow` names `**`,
and `Math.max` and `Math.min` name the array's `.max()` and `.min()`. `Math` keeps the
three members that take no value: `Math.random()`, `Math.PI` and `Math.E`.

```
Math.abs($.delta)        ✗ write $.delta.abs()
Math.pow($.b, 2)         ✗ write $.b ** 2
Math.max($.a, $.b)       ✗ write [$.a, $.b].max()
$.n.round()              → { $round: "$n" }                                  (was ["$n", 0])
$.n.floor(1)             → { $divide: [{ $floor: { $multiply: ["$n", 10] } }, 10] }
$.x.cbrt()               → { $multiply: [{ $cmp: ["$x", 0] }, { $pow: [{ $abs: "$x" }, 0.3333333333333333] }] }
$.x.sign()               → { $multiply: [{ $cmp: ["$x", 0] }, { $pow: ["$x", 0] }] }
$.x.log(10)              → { $log10: "$x" }
$.raw.trunc(2).log10()   → { $log10: { $trunc: ["$raw", 2] } }
```

`Math.sign($.x)` was `{ $cmp: ["$x", 0] }`, and the server gives `-1` for a missing
`x`. The new shape multiplies by `{ $pow: [x, 0] }`. That factor is `1` for a number and
`null` for a missing value. So `.sign()` gives `null` there, as the other arithmetic
methods do. The developer picked it over a `$cond`, because it is shorter. Because the
shape already gives `null` for `null`, the `.sign()` row states `passesNull` too, and
`$.x?.sign()` takes no `$cond`. The task planned `.sign()` without the fact. The guard
table wanted the same shape under `?.`, and the fact gives that shape. Each other
new number row states `passesNull`, and
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) measures each one.

A constant precision of `.ceil(n)` and `.floor(n)` folds the scale (`10` in place of
`{ $pow: [10, 1] }`). The mongod server gives `10 ** p` for `-7 ≤ p ≤ 15`. The fold of
a constant moves to the number methods (`(3).abs()` is `3`), for the methods whose
answer IEEE-754 specifies. The reducer wrap reads `[acc, d.x].max()` as `$max`, and
the update document reads `$.n = [$.n, 3].min()` as `$min`. A bare `Math.floor` value
or callback (`$.a.map(Math.floor)`) answers with the row's refusal. A misspelled static
never suggests a refused member. The integer hint of `.range()` names `.ceil()` and
`.floor()`.

## 2026-10-17 — feat!: the receiver methods replace the `Object` statics

JSMQL had two spellings for each object reader: the JavaScript static and the method of
the receiver. The developer's rule is "one capability gets one spelling, and the shorter
spelling wins". The method is shorter in each case, so `Object.keys`, `Object.values`,
`Object.entries`, `Object.fromEntries` and `Object.assign` are no longer JSMQL names.
They still parse, and the `Object` cell of each row refuses the call and names the
method, as `Object.groupBy` does. The `Object` root row stays, because the refusal
needs the name to parse. A suggestion for a misspelled static never names a refused
static now (`lowersOn` in [src/compiler/rows.ts](../../src/compiler/rows.ts)).

```
Object.keys($.doc)           ✗ write $.doc.keys()
Object.assign(...$.docs)     ✗ write ({}).assign(...$.docs)
Object.assign($.f, $.x);     ✗ write $.f = { ...$.f, ...$.x };
({}).assign(...$.docs)       → { $mergeObjects: "$docs" }
({}).assign($.o)             → { $mergeObjects: ["$o"] }
$.a.assign(...$.docs)        → { $mergeObjects: { $concatArrays: [["$a"], { $ifNull: ["$docs", []] }] } }
$.o.keys()                   → { $map: { input: { $objectToArray: { $ifNull: ["$o", {}] } }, in: "$$this.k" } }
$.p.fromEntries()            → { $arrayToObject: { $map: { input: { $ifNull: ["$p", []] }, in: [{ $toString: { $first: "$$this" } }, { $arrayElemAt: ["$$this", 1] }] } } }
```

`.assign()` reads a spread argument as a list of sources and a plain argument as one
source. Before, `({}).assign(...$.docs)` emitted `{ $mergeObjects: [{}, "$docs"] }`, and
the server rejects that when `docs` is an array. An empty receiver is now dropped.
After a real receiver, a spread list takes the HR5 guard of the array literal. Without
it, the server answers `{}` for `{ $mergeObjects: { $concatArrays: [["$o"], "$nope"] } }`,
so the receiver is lost. The mongod server also merges `{ $mergeObjects: ["$docs"] }`
as one list, so `["$o"]` and `"$o"` give the same answer for one plain source.

`.assign()` writes nothing in place, so the desugar rule that turned
`Object.assign(t, …);` into a write is gone, with the `mutatesArgumentAt` row fact.
lodash's `_.assign` writes its target, so a lone `$.p.assign(…)` or `r.assign(…);` is
still a statement, and the statement cell refuses it and names the write back.
`.keys()`, `.values()`, `.entries()`, `.toPairs()` and `.fromEntries()` read `$$this`
in place of a minted name, because each `in` body is fixed compiler text. The fold
now folds the method forms on a constant: `({ a: 1 }).keys()` is `["a"]`.

## 2026-10-17 — feat: a `?.` before a call that gives null for null adds no test

A `?.` before a call stops the chain with a `$cond` null test. For some operators that
test adds nothing, because the operator gives `null` for a `null` operand on its own.
The mongod server gives `null` for `$max`, `$min`, `$round`, `$ceil`, `$floor`, and for
`$objectToArray` and `$arrayToObject` over a missing value. A new row fact,
`passesNull`, states this. `stoppedChain` in
[src/compiler/emit/lower.ts](../../src/compiler/emit/lower.ts) emits the calls alone
when each call after the `?.` states the fact:

```
$.arr?.max()    → { $max: "$arr" }                                      (a $cond test before)
$.o?.keys()     → { $map: { input: { $objectToArray: "$o" }, as: "jsmqlKv", in: "$$jsmqlKv.k" } }
$.o?.a.keys()   → the $cond test stays: under the dot, .keys() runs on {} and gives []
```

The rows `keys`, `values`, `entries`, `fromEntries`, `max`, `min`, `round`, `ceil` and
`floor` state the fact. A table in
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts) measures each row
over a missing receiver and over a `null` receiver. A row that reads a missing receiver
as a value (`nullReceiverAs`) cannot state the fact, and the `NullAnswer` type refuses
the pair. The `.assign()` row does not state it, because `$mergeObjects` gives the other
operands for a `null` receiver, not `null`.

## 2026-10-17 — docs: HR5 states the number rule

HR5 gave the dot and `?.` answers for an array, an object and a string, but not for a
number. The developer's reading of the dot rule is "a dot gives the safe value, as
lodash does". [docs/LANG_RULES.md](../LANG_RULES.md) now states the dot rule for a number. A
number method on a missing or `null` receiver gives the safe value where one exists,
and `null` where none exists. `.clamp()` gives its lower bound, `.inRange()` gives
`false`, and `.range()` gives `[]`. The arithmetic methods, for example `.round()`,
have no safe value, so they give `null`. The mongod server gave these answers for `{}`:

```
$.n.clamp(0, 9)     → { $min: [{ $max: ["$n", 0] }, 9] }   → 0
$.n.round(2)        → { $round: ["$n", 2] }                → null
$.n?.clamp(0, 9)    → a $cond null test                    → null
```

The rule changes no MQL. It records the behaviour that the number rows already have,
before the `Math` members move onto the number receiver.
