## 2026-11-07 — docs: JSMQL takes its API from lodash, and the docs state what JSMQL does

JSMQL takes its API and most of its behaviour from lodash and from other
JavaScript modules that many developers know. It does not copy them exactly,
because MongoDB and the language rules decide the final answer. The docs had
sentences that said "as lodash does" or "as lodash reads it". Each such sentence
stated that JSMQL gives the answer of lodash. That statement was false where
JSMQL differs, for example for `.difference()` or for a shorthand path. The
developer asked to remove this wording.

Now only SR4 in [docs/LANG_RULES.md](../LANG_RULES.md) states the principle. The
other docs state what JSMQL does, and the reason for it: a MongoDB constraint,
or HR5. The text of HR5 has two fewer lodash clauses. The rule of HR5 does not
change.

The docs name a module in two cases only. The name can show where an API
comes from, for example `_.matches` or "the lodash methods". The name can also
warn where JSMQL differs, for example `_.isObject([])` or the duplicates of
`_.difference`.

## 2026-11-07 — feat: `.findKey(predicate)` gives the key of the first entry that passes

`.findKey()` is the object form of `.find()`. It takes the API of lodash's
`_.findKey`. The callback takes `(value, key)`. The method also takes the
property, matches and matchesProperty shorthands. Each shorthand reads the value
of the entry.

```js
$.o.findKey(v => v > 1)
// → { $getField: { field: "k", input: { $first: { $filter: {
//      input: { $objectToArray: { $ifNull: ["$o", {}] } }, as: "jsmqlKv",
//      cond: { $let: { vars: { v: "$$jsmqlKv.v" }, in: { $gt: ["$$v", 1] } } } } } } } }
$.team.findKey({ role: "admin" })   // the same MQL as $.team.findKey(x => x.role === "admin")
```

Why: before this method, a developer wrote `$.o.entries().find(([k, v]) => …)?.[0]`.
That form builds `[k, v]` pairs with a `$map`. A `$filter` then selects pairs.
Then the form reads index 0 two times, under two `$ifNull` guards.

The new
lowering applies a `$filter` to the `$objectToArray` pairs directly. It reads `k`
one time. It drops the `$map` and both guards. Its compact MQL has 206
characters, and the MQL of the old form has 264.

When no entry passes, the
answer is missing, as the answer of `.find()` is. Lodash gives `undefined`.
Under a dot, the method runs on `{}` when the receiver is missing (HR5). So the
answer is also missing. Under `?.`, the bare operators already give `null`, so
the row states `passesNull`.

The other object predicates (`.pickBy()`, `.omitBy()`) state `arrowOnly` and
refuse the shorthands. `.findKey()` states a slot layout on the object family
instead, because the shorthands are the main use of lodash's `_.findKey`. The
desugar rule needs no change, because it reads the layout of any family. The
`$filter` takes no `limit`, so the lowering needs no MongoDB 5.2 feature. The
lowering keeps the shape of `.find()`. JSMQL has no `findLastKey`, as the
developer asked.

See [src/registry/names.ts](../../src/registry/names.ts) and
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts).

## 2026-11-07 — feat: `$$ = $.items` fans out in two stages

A fan-out of a top-level field now unwinds the field in place. The compiler no
longer copies the array to a scratch slot first.

```js
$$ = $.items;
// → [{ $unwind: "$items" }, { $replaceWith: "$items" }]
$$ = $.a.b;
// → [{ $set: { "__jsmql.tmp.0": "$a.b" } }, { $unwind: "$__jsmql.tmp.0" }, { $replaceWith: "$__jsmql.tmp.0" }]
```

The rule is the same for `$$$.<coll>.concat($.items)` and
`$$$.<coll>.push(...$.items)`, because one function builds each fan-out. Why: the
`$set` stage copied a value that `$unwind` can name itself, so it added one stage
and no meaning. A run on `:27018` gave the same documents for both shapes, with
`items` as an array, one document, empty, null and missing. A dotted path keeps the
slot. `$unwind` does not traverse an array on the path, but the expression
`"$a.b"` does, so the two shapes give different documents there. An expression,
for example `$.items.map(f)`, keeps the slot too, because `$unwind` takes only a
field path. `test/compiler-statement.test.ts` runs both cases on the server.

## 2026-11-06 — feat!: `typeof` compares as written, and `"number"` names `.isNumber()`

A `typeof` comparison now has one lowering: the string you write is the string in
the MQL. `typeof x === "<s>"` is `{ $eq: [{ $type: x }, "<s>"] }` in a value, and
`{ f: { $type: "<s>" } }` in a Filter. The compiler checks each constant string
against `BSON_TYPE_ALIASES`, the closed set of names that the aggregation `$type`
can give, deprecated names included. The check also runs over each constant string
of `typeof x in [...]`. A string that is not a constant gets no check.

```js
typeof $.a === "objectId"   // → { $eq: [{ $type: "$a" }, "objectId"] }   Filter → { a: { $type: "objectId" } }
typeof $.a === "number"     // ✗ the error names $.a.isNumber()
typeof $.a === "undefined"  // ✗ the error names $.a === undefined
typeof $.a === "Object"     // ✗ the error names "object"
```

The compiler refuses `"number"`. Before, it expanded `"number"` into an `$in` over
the four number types. That expansion was a second spelling of `.isNumber()`, and
one capability gets one spelling (DEFERRED.md §B, "A second spelling for one
capability"). The compiler also refuses `"undefined"` and `"missing"`, and the error
names `x === undefined`, the one spelling of absence. Before, it took `"undefined"`
as the deprecated BSON type. `"boolean"`, `"bigint"` and `"function"` still name
`"bool"`, `"long"` and `"javascript"`. Any other string gets the closest type name,
with case ignored, or an error that states the test can never be true. The
`TYPEOF_HINTS` table holds the named spellings, and the `TYPE_GROUPS` table is gone.

We measured on mongod 9.0.2 (:27018). The aggregation `$type` never gives
`"number"`, so the expression test with `"number"` is always false. The query `$type`
refuses `"boolean"`, `"missing"` and an unknown alias with a server error. It takes
`"number"`, and matches an int, a long, a double, a decimal, and an array that holds
one. So the check also keeps HR3 for a Filter. This entry replaces part of
"2026-09-05 — fix(compiler): `typeof` speaks MongoDB's type names, and nothing else"
in [2026-09.md](2026-09.md), and the numeric group of "2026-08-16 — fix: typeof
answered differently in a filter and in an expression" in [2026-08.md](2026-08.md).
It completes "2026-11-06 — docs: `typeof` is not a second spelling of a type test".

## 2026-11-06 — feat!: `.isInteger()` and `.isNaN()` replace `Number.isInteger(x)` and `Number.isNaN(x)`

The developer moved the two Number statics to the dot syntax, as `Array.isArray` moved

No static that lowers is a callback now. So the `bareCallable` slot form reads a

the method. `test/iteratee-slots.test.ts` checks that refusal in each declared slot.

## 2026-11-06 — docs: `typeof` is not a second spelling of a type test

The developer stated that `typeof x` and a type test are two capabilities. `typeof x`
gives the type name as a string, and a program can compute with that string, for
example `(typeof $.x).toUpperCase()`. A type test gives a boolean. So `typeof` stays,
and DEFERRED.md §B does not apply to the pair. This settles the question that the
entry for the type tests left open. The bullet in
[docs/LANGUAGE.md](../LANGUAGE.md) § Type test methods said that a type test and a
`typeof` comparison give the same MQL. That was not true for a number:
`typeof $.x === "number"` is an `$in` over `$type`, and `$.x.isNumber()` is
`$isNumber`. The bullet now states the difference between the two.

## 2026-11-06 — feat: type test methods `.isString()`, `.isNumber()`, `.isUUID()` and the other type tests

The developer asked for one `.isX()` method for each type that a `.toX()` conversion
gives, and for a document. Before, a developer tested a type only with `typeof` or
with the `$type` escape hatch. Lodash's `.isString()` gave the unknown-method error, and
its suggestion named `.toString()`. The new methods are `.isString()`, `.isNumber()`,
`.isDouble()`, `.isInt()`, `.isLong()`, `.isDecimal()`, `.isBool()`, `.isDate()`,
`.isObjectId()`, `.isObject()` and `.isUUID()`. One `typeTest` helper in
[src/registry/names.ts](../../src/registry/names.ts) builds each row except `.isUUID()`.

```js
$.name.isString()   // → { $eq: [{ $type: "$name" }, "string"] }        Filter → { name: { $type: "string" } }
$.qty.isNumber()    // → { $isNumber: "$qty" }                          Filter → { qty: { $type: "number" } }
$.id.isUUID()       // → { $and: [{ $eq: [{ $type: "$id" }, "binData"] }, { $ne: [{ $convert: { input: "$id", to: "string", format: "uuid", onError: null } }, null] }] }
```

A missing receiver gives false with no `$ifNull`, because `$type` gives "missing".
MEASURED on mongod 9.0.2: `$type` names each binary subtype "binData". `$convert` to
a string with the format "uuid" fails on a subtype other than 4, and `onError` handles
that failure. `$convert` to a binData of subtype 4 does not work: `onError` does not
handle the failure of a string with no format. So `.isUUID()` tests `$type` first, and
it has no query form. `.isObject()` follows MongoDB, so an array is not a document,
unlike lodash's `_.isObject`. The boolean test is `.isBool()`, as MongoDB and
`.toBool()` name the type. Lodash's `.isBoolean()` parses, and every position refuses
it with the name `.isBool()`.

A type test is a second spelling of a `typeof` comparison, for example
`$.x.isString()` and `typeof $.x === "string"`. Both give the same MQL, and both
read an array element by element in a Filter. DEFERRED.md §B says that one capability
gets one spelling. `typeof` stays, because it also gives the type name and names every
BSON type. The developer did not decide yet whether to keep both spellings.
`Array.isArray(x)` stays the one array test, and no `.isArray()` method exists.

## 2026-11-06 — feat!: the case methods are `.toUpper()` and `.toLower()`

JSMQL now spells the two case methods `.toUpper()` and `.toLower()`. JSMQL refuses
`.toUpperCase()` and `.toLowerCase()`, and each refusal names the new spelling. The emitted MQL does not change.

```js
$.s.toUpper()                          // → { $toUpper: { $ifNull: ["$s", ""] } }
$.tags.map(t => t.trim().toLower())    // → { $map: { input: …, in: { $toLower: { $trim: … } } } }
$.s.toUpperCase()                      // ✗ refused; the message names '.toUpper()'
```

The developer chose this. The new names are the names of lodash (`_.toUpper`,
`_.toLower`) and of the MongoDB operators (`$toUpper`, `$toLower`), and they are
shorter. The rule "one capability gets one spelling, and the shorter spelling
wins" ([docs/DEFERRED.md](../DEFERRED.md) §B) keeps only one pair, so the JavaScript
names do not stay as aliases. A JavaScript developer tries the old name first, so
the old names keep a row in [src/registry/names.ts](../../src/registry/names.ts) that
refuses in every position, as `.toNumber()` does. Polarity change: JSMQL now
refuses an input that uses `.toUpperCase()` or `.toLowerCase()`.

The generated globals declare `toUpper()` and `toLower()` on `String`, because
TypeScript's library does not hold them. An arrow-form user who does not import
`@koresar/jsmql/globals` sees a type error on the new names.

## 2026-11-06 — fix: a passed-in value becomes the value that the driver sends

The driver converts some values before it sends them. It calls a value's own
`toBSON()`, and it sends a Map as a document of its entries. JSMQL did not, so the
compiled document and its printed text held a different value than the server got.
A Map printed as `{}`, and a value with `toBSON()` printed its own fields. A mongoose
document made the compiler overflow its stack.

```js
jsmql`$.m === ${new Map([["a", 1]])}`   // before → { $expr: { $eq: ["$m", {}] } }
                                        // after  → { $expr: { $eq: ["$m", { a: 1 }] } }
jsmql`$.tags === ${doc.tags}`           // a mongoose array → { $expr: { $eq: ["$tags", ["a", "b"]] } }
```

The developer chose to convert like the driver, not to refuse such values. A refusal
would make a mongoose user convert each value by hand, `doc.tags` included. Now
`driverValue` in [src/index.ts](../../src/index.ts) walks each slot and each
parameter, and it makes the driver's conversions. A Map key that is not a string is
refused, because the driver cannot send it. Polarity change: a Set, an Error, an
ArrayBuffer, a boxed primitive and a typed array other than Uint8Array are now
refused. The driver sends each one as `{}` or as index keys, which is never its data.
An object that only sets `Symbol.toStringTag` to "Date", "RegExp" or "Map" is
refused too, because `bson` reads the tag and sends the object as that kind.
The registry has a new recogniser, `isMap`, which reads the internal slot. MEASURED:
the printed text of each converted value rebuilds, in mongosh 2.13, the value that
the driver sends for the original. A filter with each value finds the document that
the driver stored on mongod. See
[docs/specs/function-form-params.md](../specs/function-form-params.md) § The value the
driver sends.

## 2026-11-06 — fix: a `?.` on a callback parameter or a `let` name reads as on a field

A `?.` on a field path adds no `$cond` test when each call after it states `passesNull`,
and the second branch of a test that stays reads the path as proven there. A `?.` on a
callback parameter or a `let` name had neither rule: it always added the test, and the
second branch still put the dot wrap on the name.

```
$.a.map(x => x?.trim())
// before: { $map: { …, in: { $cond: [{ $lte: ["$$x", null] }, null, { $trim: { input: { $ifNull: ["$$x", ""] } } }] } } }
// after:  { $map: { input: { $ifNull: ["$a", []] }, as: "x", in: { $trim: { input: "$$x" } } } }
$.a.map(x => x?.size())
// after:  { $map: { …, in: { $cond: [{ $lte: ["$$x", null] }, null, { $size: "$$x" }] } } }
```

A new Env transition, `provingName` in [src/compiler/emit/env.ts](../../src/compiler/emit/env.ts),
proves a name present, as `proving` does for a path. `stoppedChain`'s caller in
[src/compiler/emit/lower.ts](../../src/compiler/emit/lower.ts) uses it for a name in scope.

## 2026-11-06 — fix: a needle that is not a string on `.includes()` names `.has()`

`.includes(x)` tests a substring, so its needle takes a string (HR7). A needle of another

## 2026-11-06 — fix: the refusal of `.pow()` names the operator `**`

`$.n.pow(2)` said that `.pow()` is defined on `Math`. But JSMQL refuses `Math.pow` too,
because `**` says the same thing. So the hint led to a second refusal. Now one refusal
stands in every position of the `pow` row, as it does for `Number.isFinite` and

```
$.n.pow(2)          // before: ✗ '.pow()' is defined on 'Math'
                    // after:  ✗ not part of JSMQL; write $.n ** 2
Math.pow($.n, 2)    // ✗ the same refusal
$.n ** 2            // → { $pow: ["$n", 2] }
```

`pow` is the only value-taking `Math` member with no number method. Each other one, for

## 2026-11-06 — fix: a membership filter with null in the list does not select a missing field

A membership test compares as `===` does, so a missing field is not `null`. The expression
road already gave this answer. The filter road did not, because the query `$in` reads a `null`
entry as "null or missing":

```
[null, "a"].has($.s)    // before: { s: { $in: [null, "a"] } }                   selects {}
                        // after:  { s: { $in: [null, "a"], $exists: true } }    does not select {}
$.s in [null, "a"]      // the same change
$.it.some(i => [null, 5].has(i.n))   // → { it: { $elemMatch: { n: { $in: [null, 5], $exists: true } } } }
```

One helper, `queryAmong` in [src/registry/vocabulary.ts](../../src/registry/vocabulary.ts),
builds the clause for both rows. An element of `$elemMatch` is never missing, so it takes no
`$exists`. `test/compiler-query-expr-agreement.test.ts` runs the new cases on both roads.

## 2026-11-06 — feat!: JSMQL has no new keyword

The developer decided that JSMQL has no `new` keyword, for every name. `Date(…)` is the one
spelling of a date, and `ObjectId(…)`, `Long(…)` and the other BSON constructors are calls.
This is the new hard rule HR8 in `docs/LANG_RULES.md`:

```
Date("2026-01-01")             // → new Date("2026-01-01T00:00:00.000Z")
Date(2026, 0, 15)              // → new Date("2026-01-15T00:00:00.000Z")
Date()                         // → "$$NOW"
new Date("2026-01-01")         // ✗ refused at the position of `new`; the error names Date(…)
new Set([1])                   // ✗ the refusal of Set, which names the array methods
jsmql.update("$.t = Date()")   // → { $currentDate: { t: true } }
```

A polarity change: each `new X(…)` that compiled before is now refused. A new check,
`src/compiler/passes/no-new.ts`, runs on the tree as parsed, before the fold can turn
`new Date("…")` into its value. It leaves two cases to the emit phase: a name that the
program binds, because only the scope knows it, and a row that every position refuses, for
example `Set`, because its own error names the JSMQL way. `jsmql.update("$.t = Date()")`
now gives `$currentDate`; before, only `new Date()` reached it.

The registry field `newKeyword` held one value on every row after this rule, so it is gone,
with `newKeywordOf()` and the registry test that read it. A bare `Set` in an iteratee slot
now rewrites to `x => Set(x)`, and the `Set` row refuses it with the set message. The
generated `src/globals.ts` declares a call signature only for each BSON constructor. The
caller's own JavaScript keeps `new`: a `jsmql.compile` parameter, a `${…}` value, and the
printed MQL of `jsmql.stringify`.
