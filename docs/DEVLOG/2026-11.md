## 2026-11-07 — docs: the dictionary reducer spec states that `...acc` is required

A row of the body-shape table in `docs/specs/stream-methods.md` said that the

## 2026-11-07 — fix: a computed key is a string, as JavaScript makes it

`{ [k]: v }` lowered the key as it was, and `$arrayToObject` refuses a key that
is not a string. So valid JavaScript gave MQL that the server refused, for
example `{ [$.a]: 1 }` over a number, `$.items.reduce((acc, x) => ({ ...acc, [x]:
(acc[x] ?? 0) + 1 }), {})` over numbers, and the stream reducer wrap
`$$ = [$$.reduce((acc, d) => ({ ...acc, [d._id]: d }), {})]`.

A computed key is now `{ $toString: { $ifNull: [k, ""] } }` (`propertyKeyExpr` in
`registry/mql.ts`). A constant number or boolean key is its text (`{ [7]: 1 }`
gives the key `"7"`). A key that the proof shows is a string stays as it is. A
null or missing key is `""`, because a read `o[k]` uses `""` for the same value.
So a count that writes `[s]` and reads `acc[s]` uses one key. JavaScript uses
`"null"` there, and LANGUAGE.md § Computed Keys states the difference.

## 2026-11-07 — fix: a playground refresh restores the work of its own tab

Two tabs of the playground shared one `localStorage` key. Each edit wrote the
whole session. So a refresh of one tab showed the work of the tab that saved
last, and the work of the first tab was gone from storage. The session now goes to
two stores. `sessionStorage` belongs to one tab and survives its refresh, and

## 2026-11-07 — fix: a raw `$$ROOT` reads the document without `__jsmql`

HR1 keeps a raw `"$$ROOT"` as written. So after a `let`, a raw stage such as
`$group({ _id: null, all: { $push: "$$ROOT" } })` put the `__jsmql` fields into
each element of `all`. A raw `$$ROOT` in a `$match` also counted them:
`{ $size: { $objectToArray: "$$ROOT" } }` gave one field too many.

When the namespace may be on the document, `clearOfNamespace` now puts
`{ $unset: "__jsmql" }` ahead of a statement that holds a raw `$$ROOT` or
`$$CURRENT`. The walk skips each sub-pipeline, by the row's `statement` or
`stream` slot. A binding from an earlier statement is gone. The compiler refuses a later read
of it, and names `$` as the fix. The compiler also refuses a statement that
reads the namespace, because it cannot remove what the statement reads. `$` is the
spelling that keeps the bindings: `$push($)` gives
`{ $push: { $unsetField: { field: "__jsmql", input: "$$ROOT" } } }`.

The stages of a row that states `restoresDocuments` (`.uniq()`, `.uniqBy()`)
keep the bare `$$ROOT` on purpose, so that a later link still reads a `let`.
They mark it with `carriesRoot` in `registry/mql.ts`, and the walk skips them.
The keyed reducer wrap (`[d.id]: d`) now reads the whole document through the
chain too. The counter `Chain.wrote` became `Chain.writes`, which counts every
write under the namespace. So a statement that writes nothing there leaves the
flag false after the `$unset`.

## 2026-11-07 — fix: a parameter that holds an Invalid Date is refused

The driver sends an Invalid Date as the epoch. A compile parameter or a

## 2026-11-07 — fix: a read of the whole document leaves out the compiler's namespace

The trailing `{ $unset: "__jsmql" }` removes the top-level field only. A read
of the whole document as a value copied the namespace into that value, and the
documents of the pipeline held it. MEASURED on `:27018`, each of these gave
back a field under `__jsmql`:

- `let t = $.a + 1; $ = { ...$, y: t }` and `$ = $` — the replace also cleared
  the cleanup flag;
- `$.copy = $`, `$group({ _id: null, all: $push($) })`, `$$ = $$.map(d => d)`,
  `.map(d => ({ d }))`;
- `$$.groupBy(…)` and `$$.keyBy(…)`, for example after `.shuffle()`, which
  writes `__jsmql.tmp.0`. `permutations.test.ts` ran this chain and passed,
  because it checked only that the server accepts the pipeline;
- `$.copy = { d: $, n: $$.size() }` and the same read in a `$facet` branch. The
  compiler lowered `$` before `$$.size()` hoisted the stage that writes
  `__jsmql.size`, so a check at the read alone cannot see it.

A read of the whole document now asks its chain (`Chain.wholeDocument`). While
the namespace may be there, the read is
`{ $unsetField: { field: "__jsmql", input: "$$ROOT" } }`; otherwise it stays the
bare `"$$ROOT"`. A statement can read the document bare, and then place a stage
ahead of the read that writes the namespace. That statement lowers again
(`clearOfNamespace`). `Chain.mark()` and `rewind()` now also put back `dirty`,
`element` and `terminal`. A raw stage that keeps the bare `$$ROOT`
(`$replaceWith("$$ROOT")`) keeps the cleanup. The registry rows of `$`,
`.groupBy()` and `.keyBy()` read the new `wholeDocument` service. They no longer
contain the string `"$$ROOT"`.

Both the statement suite and the permutation suite now look for `__jsmql` at
every depth of each document that a live run gives back.

## 2026-11-07 — docs: JSMQL takes its API from lodash, and the docs state what JSMQL does

JSMQL takes its API and most of its behaviour from lodash and from other
JavaScript modules that many developers know. It does not copy them exactly,
because MongoDB and the language rules decide the final answer. The docs had
sentences that said "as lodash does" or "as lodash reads it". Each such sentence

JSMQL differs, for example for `.difference()` or for a shorthand path. The
developer asked to remove this wording.

Now only SR4 in [docs/LANG_RULES.md](../LANG_RULES.md) states the principle. The
other docs state what JSMQL does, and the reason for it: a MongoDB constraint,

change.

The docs name a module in two cases only. The name can show where an API
comes from, for example `_.matches` or "the lodash methods". The name can also
warn where JSMQL differs, for example `_.isObject([])` or the duplicates of
`_.difference`.

## 2026-11-07 — feat!: the three pads take a constant length and one ASCII character

`.padStart()`, `.padEnd()` and `.pad()` now take a constant length of 1 or
more and a pad of one ASCII character. JSMQL refuses a length from the data, a
pad of two or more characters, an empty pad and a non-ASCII pad. This supersedes
the rules of the entry "feat: `.pad(length[, chars])` pads both sides, as
`_.pad` does" below. Why: JSMQL is for analytics, and analytics needs a fixed
width with one character. A developer who needs other padding writes the MQL
with `$reduce` and `$concat`.

```js
$.code.padStart(5, "0")
// → { $let: { vars: { jsmqlPad: { $ifNull: ["$code", ""] } },
//      in: { $reduce: { input: { $range: [5, { $strLenCP: "$$jsmqlPad" }, -1] },
//        initialValue: "$$jsmqlPad", in: { $concat: ["0", "$$value"] } } } } }
$.code.pad(9)
// → the same $reduce, with in: { $cond: [{ $mod: ["$$this", 2] },
//      { $concat: ["$$value", " "] }, { $concat: [" ", "$$value"] }] }
```

The narrow rules give one small shape for all three. One `$reduce` adds the
pad once for each missing character, and its `$range` counts down from the
length to the length of the string. The range is empty when the string is
long enough, so no guard is necessary. `.pad()` adds at the end on the first
step and then at the start, so the end takes the odd character, as lodash
does. `$.code.pad(9)` shrinks from 410 to 250 characters of MQL, and
`$.code.padStart(5, "0")` from 220 to 188, as compact JSON. A constant fill string, such as
`"00000"`, is smaller for a short length. We rejected it, because its size
grows with the length. A new argument rule,
`oneChar` in [src/registry/vocabulary.ts](../../src/registry/vocabulary.ts),
refuses the pad. `.padEnd()` no longer states `passesNull`, because
`$strLenCP` refuses the null that `$concat` passed through. JSMQL now
refuses a dynamic length or pad, a multi-character pad and an empty pad. The
compiler accepted them before.

## 2026-11-07 — feat: `.pad(length[, chars])` pads both sides, as `_.pad` does

The string method `.pad()` joins `.padStart()` and `.padEnd()`. It pads both
sides of the string to `length`. The start takes the floor of half the padding,
and the end takes the ceil. Each side repeats `chars` from its first character.

```js
"abc".pad(8, "_-")   // → "_-abc_-_"
$.s.pad(9)           // → { $let: { vars: { jsmqlPad: { $ifNull: ["$s", ""] } },
                     //       in: { $let: { vars: { jsmqlHalf: { $divide: [{ $subtract: [9, { $strLenCP: "$$jsmqlPad" }] }, 2] } },
                     //         in: { $concat: [<floor fill>, "$$jsmqlPad", <ceil fill>] } } } } }
```

The row uses the helper of `.padStart()` and `.padEnd()`, with a third side.
One `$let` holds half the padding, because each side reads it twice. A missing
receiver pads the empty string, as lodash does (HR5). The length takes an
integer and the pad takes a string (HR7). Why: a lodash gap review found that
`.pad()` was the one missing member of the pad family.
`test/compiler-methods.test.ts` compares each case with a JavaScript version of
`_.pad` on the server. The cases cover an odd and an even padding, a pad of
several characters and an empty pad. They also cover a short length, a length
from the data and a missing field.

## 2026-11-07 — feat: `.invertBy([iteratee])` groups the keys of an object by a computed value

JSMQL now has lodash's `_.invertBy` as an object method. The result maps each
iteratee result, as a string, to the list of original keys that gave it. Each
list keeps the entry order. With no iteratee, the value itself is the key.

```js
$.o.invertBy()               // { a: 1, b: 2, c: 1 } → { "1": ["a", "c"], "2": ["b"] }
$.team.invertBy("role")      // the same shorthands as .groupBy(): "field", an index, { k: v }, ["k", v]
```

Why: `.invert()` loses every key but the last when two keys hold one value.
`.invertBy()` is the lodash method that keeps every key, and it maps cleanly
to MQL. The lowering computes each key once in a `$let`, then gives one list
per distinct key. Lodash passes the iteratee the value only. So the row takes
the array `iteratee` service and an `object` slot layout. It does not take the
`(value, key)` arrow of `.mapValues()`. A key is stringified as `.groupBy()`
does it, so a missing or null result gives the key `"null"`. A live mongod checked each shape against a
lodash-equivalent answer: numbers, booleans, null, a collision, an empty object
and a missing field. See [src/registry/names.ts](../../src/registry/names.ts) and
[docs/LANGUAGE.md](../LANGUAGE.md).

## 2026-11-07 — feat: `.findKey(predicate)` gives the key of the first entry that passes

`.findKey()` is the object form of `.find()`. It takes the API of lodash's
`_.findKey`. The callback takes `(value, key)`. The method also takes the
property, matches and matchesProperty shorthands. Each shorthand reads the value
of the entry.

```js
$.o.findKey(v => v > 1)
// → { $getField: { field: "k", input: { $first: { $filter: {
//      input: { $objectToArray: { $ifNull: ["$o", {}] } }, as: "jsmqlKv",
//      cond: { $let: { vars: { v: "$$jsmqlKv.v" }, in: { $gt: ["$$v", 1] } } } } } } } }
$.team.findKey({ role: "admin" })   // the same MQL as $.team.findKey(x => x.role === "admin")
```

Why: before this method, a developer wrote `$.o.entries().find(([k, v]) => …)?.[0]`.
That form builds `[k, v]` pairs with a `$map`. A `$filter` then selects pairs.
Then the form reads index 0 two times, under two `$ifNull` guards.

The new
lowering applies a `$filter` to the `$objectToArray` pairs directly. It reads `k`
one time. It drops the `$map` and both guards. Its compact MQL has 206
characters, and the MQL of the old form has 264.

When no entry passes, the
answer is missing, as the answer of `.find()` is. Lodash gives `undefined`.
Under a dot, the method runs on `{}` when the receiver is missing (HR5). So the
answer is also missing. Under `?.`, the bare operators already give `null`, so
the row states `passesNull`.

The other object predicates (`.pickBy()`, `.omitBy()`) state `arrowOnly` and
refuse the shorthands. `.findKey()` states a slot layout on the object family
instead, because the shorthands are the main use of lodash's `_.findKey`. The
desugar rule needs no change, because it reads the layout of any family. The
`$filter` takes no `limit`, so the lowering needs no MongoDB 5.2 feature. The
lowering keeps the shape of `.find()`. JSMQL has no `findLastKey`, as the
developer asked.

See [src/registry/names.ts](../../src/registry/names.ts) and
[test/compiler-methods.test.ts](../../test/compiler-methods.test.ts).

## 2026-11-07 — feat: `$$ = $.items` fans out in two stages

A fan-out of a top-level field now unwinds the field in place. The compiler no
longer copies the array to a scratch slot first.

```js
$$ = $.items;
// → [{ $unwind: "$items" }, { $replaceWith: "$items" }]
$$ = $.a.b;
// → [{ $set: { "__jsmql.tmp.0": "$a.b" } }, { $unwind: "$__jsmql.tmp.0" }, { $replaceWith: "$__jsmql.tmp.0" }]
```

The rule is the same for `$$$.<coll>.concat($.items)` and
`$$$.<coll>.push(...$.items)`, because one function builds each fan-out. Why: the
`$set` stage copied a value that `$unwind` can name itself, so it added one stage
and no meaning. A run on `:27018` gave the same documents for both shapes, with
`items` as an array, one document, empty, null and missing. A dotted path keeps the
slot. `$unwind` does not traverse an array on the path, but the expression

## 2026-11-06 — feat!: `typeof` compares as written, and `"number"` names `.isNumber()`

A `typeof` comparison now has one lowering: the string you write is the string in
the MQL. `typeof x === "<s>"` is `{ $eq: [{ $type: x }, "<s>"] }` in a value, and
`{ f: { $type: "<s>" } }` in a Filter. The compiler checks each constant string
against `BSON_TYPE_ALIASES`, the closed set of names that the aggregation `$type`
can give, deprecated names included. The check also runs over each constant string
of `typeof x in [...]`. A string that is not a constant gets no check.

```js
typeof $.a === "objectId"   // → { $eq: [{ $type: "$a" }, "objectId"] }   Filter → { a: { $type: "objectId" } }
typeof $.a === "number"     // ✗ the error names $.a.isNumber()
typeof $.a === "undefined"  // ✗ the error names $.a === undefined
typeof $.a === "Object"     // ✗ the error names "object"
```

The compiler refuses `"number"`. Before, it expanded `"number"` into an `$in` over
the four number types. That expansion was a second spelling of `.isNumber()`, and
one capability gets one spelling (DEFERRED.md §B, "A second spelling for one
capability"). The compiler also refuses `"undefined"` and `"missing"`, and the error
names `x === undefined`, the one spelling of absence. Before, it took `"undefined"`
as the deprecated BSON type. `"boolean"`, `"bigint"` and `"function"` still name
`"bool"`, `"long"` and `"javascript"`. Any other string gets the closest type name,
with case ignored, or an error that states the test can never be true. The
`TYPEOF_HINTS` table holds the named spellings, and the `TYPE_GROUPS` table is gone.

We measured on mongod 9.0.2 (:27018). The aggregation `$type` never gives
`"number"`, so the expression test with `"number"` is always false. The query `$type`
refuses `"boolean"`, `"missing"` and an unknown alias with a server error. It takes
`"number"`, and matches an int, a long, a double, a decimal, and an array that holds
one. So the check also keeps HR3 for a Filter. This entry replaces part of
"2026-09-05 — fix(compiler): `typeof` speaks MongoDB's type names, and nothing else"
in [2026-09.md](2026-09.md), and the numeric group of "2026-08-16 — fix: typeof
answered differently in a filter and in an expression" in [2026-08.md](2026-08.md).
It completes "2026-11-06 — docs: `typeof` is not a second spelling of a type test".

## 2026-11-06 — fix: a passed-in value becomes the value that the driver sends

The driver converts some values before it sends them. It calls a value's own
`toBSON()`, and it sends a Map as a document of its entries. JSMQL did not, so the

refused, because the driver cannot send it. Polarity change: a Set, an Error, an

refused too, because `bson` reads the tag and sends the object as that kind.
The registry has a new recogniser, `isMap`, which reads the internal slot. MEASURED:
the printed text of each converted value rebuilds, in mongosh 2.13, the value that
the driver sends for the original. A filter with each value finds the document that
the driver stored on mongod. See
[docs/specs/function-form-params.md](../specs/function-form-params.md) § The value the
driver sends.

the first read is a value over the joined slot. A stream method after such a read, for example

the general refusal of a join chain. See
[src/compiler/emit/join.ts](../../src/compiler/emit/join.ts) `lookupOf` and
[docs/specs/emit-pass.md](../specs/emit-pass.md) § The join road. The cases are in
